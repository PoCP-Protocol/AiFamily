## 1. 总体判断

### 1.1 不是教育 App，而是家庭成长平台

教育是切入场景，不是最终品类。Family 的长期定位是：

> 以孩子成长为价值中心，以家庭为服务和商业单元，以 AI 为理解、编排和协作中枢，连接学校、老师、专家、机构、社区和家庭产品，帮助家庭看见需要、找到资源、采取行动、持续复盘。

孩子是价值中心，但不是唯一直接用户；家庭是系统边界、长期关系和商业单元；家长通常是付款人、主要授权人和重大决定者。

### 1.2 不是三个模式并列，而是一个多边平台

三种模式的分工是：

- B2C 是平台的根：建立家庭关系、形成现金流、沉淀经授权的长期上下文；
- B2B2C 是平台的放大器：连接学校、机构、社区和企业家庭福利，降低获客和交付成本；
- C2C 是平台的网络层：形成家庭之间的互助、共同活动和经验传播；
- AI 是平台的编排层：把内容和资源转成家庭可执行的行动，不是单独售卖的聊天机器人。

### 1.3 不是普通短视频平台，而是“内容到行动”的平台

可以学习短视频平台的分发、创作者和直播能力，但不能把商业目标定义成最大化刷屏时间。Family 的北极星是：

> 每个活跃家庭在一个周期内完成一次经确认、可回读、可复盘的有效行动。

内容只是入口；家庭行动、专业服务、履约和复盘才是价值闭环。

### 1.4 不是普通商城，而是家庭需要的解决方案网络

商品必须从家庭已经表达或确认的需要进入，而不是从库存、广告或孩子画像反向刺激需求。平台的扩展方向是：

```text
家庭需要 → 解释与确认 → 成长/关系方案 → 服务与商品履约 → 反馈与复盘
```

## 2. 价值主张与服务对象

### 2.1 对孩子

平台为孩子提供：

- 更适合其年龄和处境的成长支持；
- 被家长和专业人员理解的机会；
- 参与家庭行动的空间；
- 兴趣、能力、关系和生活体验的成长资源；
- 不被家庭总分、跨家庭排名和商业画像定义的安全环境。

孩子不是平台的广告受众，也不是被系统自动处置的对象。

### 2.2 对家长

平台为家长提供：

- 对孩子和家庭处境的更清晰理解；
- 可解释的假设和下一步建议；
- 可执行的 21 天行动和 90 天计划；
- AI 与真人共同陪跑；
- 老师、专家、机构、活动和商品的可信选择；
- 家庭成员之间的协作工具；
- 对家庭数据、授权、服务和消费的控制权。

### 2.3 对家庭整体

平台要改善的不是某一个孩子的单点成绩，而是家庭系统：

- 亲子沟通；
- 家庭规则和节奏；
- 家长协作；
- 孩子的自驱、习惯、兴趣和关系；
- 家庭与学校、社会资源的连接；
- 家庭共同活动和共同成长。

### 2.4 对老师、专家和机构

平台为供给方提供：

- 合法、透明、可控的家庭服务需求；
- 明确的任务边界和交付标准；
- 案件、任务、预约、履约、验收和贡献确认工具；
- 经过授权的最小必要上下文；
- 结算、质量反馈和争议处理机制。

老师、专家或机构不能“拥有”家庭，也不能把家庭直接带离平台形成私域归属。

### 2.5 对学校和社会伙伴

平台帮助伙伴提供家庭服务和成长支持，但不把伙伴变成家庭数据的所有者。合作方获得的是：

- 授权范围内的协同信息；
- 项目和服务交付工具；
- 脱敏、聚合、目的限定的运营输出；
- 可审计的合作与结算凭证。

## 3. 平台业务总模型

### 3.1 四个同心层

Family 采用四个同心层，而不是把所有功能平铺成商城：

#### 第一层：孩子成长

内容、测评、兴趣、习惯、关系、行动和成长证据。

#### 第二层：家庭关系

亲子沟通、家庭规则、家庭任务、家长协作、家庭活动和家庭复盘。

#### 第三层：社会资源

学校、老师、专家、机构、社区、活动和合作伙伴。

#### 第四层：家庭消费

课程、图书、工具、活动、设备、服务和其他家庭需要的产品。

第四层必须服从前面三层，不能反过来用商品和广告改变家庭需求。

### 3.2 八层价值到产品的翻译

现有目标架构的八层，在平台产品中的对应关系是：

- Family Experience：家长、孩子、家庭、老师、专家、机构的实际体验；
- Value Experience：情绪安全、行动改变、成长支持、家庭经济价值和信任；
- Family Growth Intelligence：Family Context、Family Growth Graph、主要矛盾、干预策略和证据；
- Product Intelligence：内容、产品和服务需求的信号、洞察、机会和版本；
- Service Intelligence：方案、案件、任务、资源匹配和 FGCN 交付；
- AI Runtime：模型网关、上下文、Agent、工具、安全、Human Gate、评估和追踪；
- Data Platform：领域事实、投影、事件、审计、留存和派生数据；
- Model Layer：可替换的模型和多模态供应商。

AI Runtime 不直接拥有家庭事实；模型不成为业务架构的中心；平台护城河在家庭长期上下文、服务网络和交付闭环的组合。

### 3.3 家庭生命周期

一个家庭在平台内经历的目标生命周期是：

```text
发现/被触达
→ 建立家庭边界
→ 目的化同意
→ 识别家庭需要
→ 测评与证据冻结
→ 假设解释与家庭确认
→ 形成成长意图
→ 生成或选择计划
→ 今日行动与家庭协作
→ 必要时连接专业服务
→ 服务履约与成果证据
→ 家庭复盘与下一阶段选择
→ 会员续费、服务复购或方案扩展
```

每一步都应有成功、拒绝、暂停、取消、过期、重试、人工接管和数据权利路径。

### 3.4 组合对标，不做单一平台复制

家庭成长平台没有一个可以完整复制的单一标杆，应按能力层组合学习：

- 抖音/TikTok：内容分发、短视频、直播和创作者工具；
- 小红书：家庭问题搜索、经验内容、决策和内容到商品；
- B 站/知乎：知识内容、专业解释、创作者信任和长内容沉淀；
- Keep/Duolingo：从内容到计划、行动、反馈和持续习惯；
- ClassDojo：家校沟通、老师与家长协作；
- Cozi/OurHome：家庭日历、任务和成员协同；
- Khan Academy/Khanmigo：分层解释、个性化辅导和 AI 学习辅助；
- 美团/Airbnb：供给准入、预约、履约、评价、退款和争议；
- 京东/亚马逊：商品主数据、订单、支付、售后和供应链履约。

这些平台只能提供局部产品基因。Family 的组合方式应是：

```text
内容分发
+ 家庭问题理解
+ 家庭行动闭环
+ 专业服务网络
+ 商品与权益履约
+ 家庭关系与数据治理
```

不能把“播放时长最大化”“孩子沉迷式连续推荐”“家庭排名”“纯广告变现”作为平台底层机制。

## 4. 三种商业模式的系统设计

### 4.1 B2C：家庭关系和现金流的基础

#### 4.1.1 客户结构

- 家庭是账户和长期服务单元；
- 家长是主要付款和授权主体；
- 孩子是成长受益者和部分行动参与者；
- 其他家庭成员按角色获得可见性和操作权限。

#### 4.1.2 产品阶梯

建议采用四级产品阶梯：

1. 触达层：公开内容、短视频、直播、家庭问题搜索和基础工具；
2. 体验层：家庭测评、问题理解、短期行动或低价体验方案；
3. 会员层：持续 AI 陪伴、家庭上下文、21 天行动、90 天计划、家庭复盘和优先服务；
4. 服务层：家长辅导、亲子关系、老师/专家咨询、机构方案、家庭活动和组合产品。

体验层的目标不是一次性卖测评，而是让家庭完成第一段有效行动；会员层的目标不是无限增加功能，而是持续维护家庭关系和成长闭环。

#### 4.1.3 B2C 收入

B2C 可形成以下收入来源：

- 家庭会员订阅；
- 家庭专项方案和成长营；
- 老师、专家和机构服务费；
- 家庭活动和预约服务费；
- 方案关联的商品交易服务费；
- 会员权益和增值服务。

不以出售孩子画像、跨家庭排名、隐藏广告和向孩子自动营销作为收入来源。

### 4.2 B2B2C：供给、渠道和规模化交付

#### 4.2.1 三种合作交易形态

第一种是伙伴推荐：学校、老师、社区或机构把家庭带入平台，家长自主注册和购买。

第二种是伙伴采购：学校、机构、企业福利平台或社区采购一组家庭服务，家庭在授权范围内使用。

第三种是平台代交付：平台为机构组织老师、专家和服务资源，按项目或按已验收任务结算。

这三种形态必须在合同、付款主体、数据目的、服务责任和退款责任上分别建模，不能用一个“机构用户”字段混在一起。

#### 4.2.2 B2B2C 的责任边界

- 机构购买服务能力，不自动取得家庭全部数据；
- 家庭授权必须单独记录，不能用机构合同替代个人同意；
- 学校和老师只读取完成具体任务所需的最小信息；
- 机构输出优先使用聚合和脱敏结果；
- 高影响评估、敏感动作和权益决定必须保留人工复核；
- 机构退出、合同终止和家庭撤回后，数据访问和服务权限立即收敛。

#### 4.2.3 B2B2C 收入

- 年度平台许可费；
- 按家庭/项目/服务单元采购；
- 机构服务管理费；
- 经过验收的专业服务交付费；
- 机构版运营和质量管理模块。

不把家庭数据销售给机构作为收入模型。

### 4.3 C2C：家庭之间的关系和网络效应

C2C 首先是家庭互助网络，之后才是交易网络。适合的形态包括：

- 家长经验分享；
- 家庭活动和兴趣小组；
- 家庭共同任务；
- 亲子活动组队；
- 家庭之间的低风险物品或活动协作；
- 经平台审核的家庭内容和服务体验分享。

C2C 的平台规则：

- 默认保护家庭隐私，家庭内容可控分享；
- 内容和群组需要审核、举报、申诉和撤回；
- 不做家庭总分、家庭排名和孩子比较榜单；
- 不把普通家长包装为未经审核的“专家”；
- 不允许通过无限层级裂变形成传销式激励；
- 高风险服务进入平台供给准入和人工审核流程。

开放式教师/专家市场不是能力禁区，但不能以“谁都能开店、平台只负责撮合”的方式建设。真正上线的专家服务必须具有资质、任务、履约、验收、争议和结算闭环。

### 4.4 综合收入模型

长期收入组合可以表达为：

```text
家庭会员
+ 家庭专项服务
+ 专业服务交易
+ 精选商品和活动交易
+ 机构采购与平台许可
+ 受控家庭网络服务
```

商业重心应从低毛利流量广告逐步转向高信任、高复购、高履约质量的家庭服务关系。

### 4.5 四本账

三种商业模式共用四本相互独立的账：

1. 产品账：记录 Offer、Order、Payment、Entitlement，回答卖了什么、谁付款、获得什么；
2. 交付账：记录 ServiceCase、Task、Delivery、Verification，回答谁完成了哪项服务、家庭是否验收；
3. 贡献账：记录 Contribution 和 AllocationStatement，按已验收任务形成分配依据；
4. 质量账：记录投诉、返工、退款、质量储备和释放状态。

产品账不能替代交付账，交付账不能直接产生贡献账，贡献账不能绕过质量账直接结算。四本账必须可独立审计、对账和回放。

## 5. 产品总体结构

### 5.1 家庭入口与家庭首页

家庭首页不是单纯的信息流，而是家庭当前状态的行动入口，至少包括：

- 家庭当前正在关注的需要；
- 今日或本阶段行动；
- 家庭成员协作状态；
- 已确认的服务和预约；
- 家庭内容收藏与待处理事项；
- 待家长确认的 AI 草案；
- 重要提醒、同意和数据权利入口；
- 不带家庭排名的私有回顾和成果记录。

首页可以展示内容，但内容必须与家庭行动空间相连。

### 5.2 内容与直播中心

内容中心承担触达、教育、经验和资源发现，支持：

- 短视频；
- 图文和长内容；
- 直播和回放；
- 专题、课程和活动；
- 专业问答；
- 家庭故事和经验分享；
- 内容收藏、转发、家庭共看和行动引用。

内容不是事实来源的自动替代物。专业内容必须有来源、作者身份、适用范围、版本和审核状态。

### 5.3 家庭成长工作台

成长工作台承载：

- 家庭需要和目标；
- 测评执行与证据冻结；
- 假设解读和家庭确认；
- 21 天行动；
- 90 天计划；
- 阶段复盘；
- 家庭成员反馈；
- 经过同意的成长记录和成果。

“成长”不能被一个总分概括。平台应该展示时间、证据、行动和反馈的变化。

### 5.4 AI 家庭助手

AI 助手提供：

- 家庭问题澄清；
- 资料和内容解释；
- 计划和行动草案；
- 家庭沟通准备；
- 资源发现和服务匹配；
- 进度提醒；
- 阶段复盘问题；
- 必要时升级到真人服务。

高影响动作不能由 AI 单独完成，例如诊断性质结论、敏感家庭计划变更、教师或服务推荐确认、购买、会员升级、对外沟通和涉及未成年人的敏感动作。

### 5.5 专业服务中心

服务中心支持：

- 老师、专家和机构发现；
- 服务详情、资质和适用范围；
- 时段、预约、取消和改派；
- 服务记录；
- 服务案件和任务；
- 人工复核、质量反馈和投诉；
- 服务结果和后续建议。

服务中心与内容中心的关系是“内容建立信任，服务解决具体问题”，不能把内容作者身份自动等同于服务资格。

### 5.6 家庭方案与商品中心

商品中心提供：

- 商品目录和版本；
- 家庭方案中的商品组成；
- 价格、库存、适用范围和供应商；
- 购买、支付、退款、权益和售后；
- 会员权益和积分账本；
- 交易、返佣、结算和对账。

购买入口必须说明“为什么适合当前家庭需要”，并允许家长拒绝个性化推荐或选择非个性化目录。

### 5.7 家庭社区

社区支持：

- 家庭经验发布；
- 家长互助；
- 活动和兴趣组；
- 家庭共同行动；
- 内容举报、审核、申诉和删除；
- 分享范围和家庭成员可见性控制。

社区内容不能变成公开展示孩子隐私、家庭经营状况或成长排名的场所。

### 5.8 家庭账户与信任中心

信任中心集中处理：

- 家庭成员和关系；
- 角色和权限；
- 目的化同意；
- 数据访问、更正、导出和删除；
- 内容分享和撤回；
- 订单、权益和支付安全；
- AI 输出解释、人工复核和申诉。

### 5.9 五个一级入口

34 个 UI 不应继续作为互相孤立的页面，而应重组为五个一级入口：

- `Today`：家庭今天做什么，包括今日行动、提醒、家庭协作和正在进行的服务；
- `Growth`：测评、AI 解读、成长需要、21/90 天计划、行动、复盘和私有成果；
- `Discover`：内容、直播、专题、方案、商品、会员和家庭社区；
- `Services`：管家、教师、专家、机构、活动、预约、案件、交付和验收；
- `Mine`：家庭账户、成员、可见性、同意、数据权利、订单、资产和会员。

需要重点建设的跨入口页面包括：

- 家庭需求中心；
- 内容详情与直播间；
- AI 对话与解释页；
- 家庭方案工作台；
- 服务案件跟踪页；
- 家庭协同空间；
- 同意、可见性和数据权利中心。

入口划分是体验组织方式，不改变领域的唯一事实归属。一个业务事实可以被多个入口以只读投影展示，但只能由其权威领域写入。

### 5.10 统一页面状态和失败路径

所有端都应使用一致的可解释状态：

- `Loading`：说明正在读取什么；
- `Empty`：说明为什么没有数据以及下一步是什么；
- `Draft`：明确建议尚未确认；
- `Review Required`：明确需要家庭或人工确认；
- `Success`：展示真实事实、来源和时间；
- `Paused`：展示暂停位置、原因和恢复方式；
- `Denied`：说明权限或同意不足；
- `Error`：提供重试、稍后处理或转人工；
- `Deleted/Expired`：说明失效原因和重新开始方式。

关键失败路径必须在产品和后端同时成立：

- AI 上下文不足：要求家庭补充表达，不编造结论；
- 模型超时：明确未生成，可重试或转人工；
- 高风险内容：停止自动处理，进入 Human Gate；
- 计划重复提交：幂等返回原回执；
- 计划版本冲突：提示刷新，不覆盖家庭最新选择；
- 服务无合资格人员：进入待匹配，不虚构已安排；
- 时段冲突：释放占用并允许重新选择；
- 交付不满意：创建返工、换人或投诉流程；
- 支付失败：订单不成功、权益不激活；
- 退款处理中：不提前宣称退款完成；
- 社区审核未通过：说明原因，允许修改或申诉；
- 撤回同意：立即停止对应处理并启动派生数据清理。

## 6. 核心业务闭环

### 6.1 内容到家庭进入

```text
内容/直播/活动触达
→ 家长表达家庭问题
→ 解释服务边界和数据目的
→ 建立家庭与成员边界
→ 取得所需同意
→ 进入测评或行动体验
```

失败路径包括：不同意、未达到年龄/权限条件、内容不适用、无法确认家庭关系、重复进入和幂等重放。

### 6.2 测评到成长意图

```text
选择测评目的
→ 执行测评
→ 冻结回答和证据版本
→ 生成 AI Perspective/Hypothesis
→ 展示依据、局限和不确定性
→ 家庭确认或拒绝
→ 形成 GrowthIntent
```

AI 假设不能自动写入家庭事实；家庭确认后形成的是成长意图或待执行建议，不代表医学诊断或永久人格标签。

### 6.3 成长意图到计划和行动

```text
GrowthIntent
→ 识别当前主要矛盾
→ 选择或生成 Service Blueprint
→ 家庭确认 21/90 天计划
→ 生成今日行动
→ 家庭成员参与
→ 记录过程事实和证据
→ 阶段复盘或暂停
```

主要矛盾是帮助平台从“问题清单”转到“当前最值得解决的事情”，但不能把它变成一个自动诊断标签。

### 6.4 需要到服务

```text
家庭确认需要真人帮助
→ 服务需求单
→ 资格/能力/容量/连续性/偏好匹配
→ 预约或 FGCN 案件
→ 任务分派
→ 交付与证据
→ 家庭验收
→ 质量回访
→ 贡献确认与结算
```

### 6.5 方案到商品

```text
家庭需要已确认
→ 方案说明适用范围和替代项
→ 家长确认推荐
→ 商品/服务订单
→ 支付或权益使用
→ 履约
→ 退款/售后
→ 结果反馈
```

购买意向、订单、支付、权益、积分和结算是不同事实，不能用一个状态或一个硬编码余额替代。

### 6.6 家庭行动到持续关系

```text
内容/服务完成
→ 家庭反馈
→ 结果证据归档
→ AI 形成下一轮草案
→ 家长确认
→ 续费、复购、暂停或退出
```

持续关系依靠有效帮助和信任，不依靠强制打卡、排名或焦虑通知。

## 7. 核心领域和业务对象

### 7.1 身份与家庭域

核心对象：

- Account；
- Person；
- Family；
- FamilyMembership；
- Relationship；
- Role；
- Tenant；
- TenantFamilyBinding；
- ConsentGrant；

### 7.2 内容域

核心对象：

- CreatorProfile；
- ContentDraft；
- ContentVersion；
- MediaAsset；
- LiveSession；
- Topic；
- ContentApplicability；
- ContentModerationCase；
- ContentActionReference；
- ContentFeedback。

内容状态建议为：

```text
DRAFT → REVIEWING → PUBLISHED → LIMITED/PAUSED → RETIRED
```

AI 生成的内容默认是草案，不能绕过审核直接变成可发布内容。

### 7.3 成长与评估域

不得创建家庭总分、家庭排名或用跨家庭比较字段替代成长过程。

### 7.4 计划与方案域

### 7.5 服务与 FGCN 域


积分和权益必须有正式账本或权威事件依据。没有数据时返回明确的“暂无数据”，不能使用静默硬编码余额。

## 8. 内容平台设计

### 8.1 内容分类

内容至少分为：

- 家庭问题解释；
- 亲子沟通示范；
- 学习与习惯支持；
- 家庭活动和兴趣；
- 家长成长；
- 专业服务介绍；
- 商品和工具说明；
- 家庭经验分享；
- 机构项目和公益资源。

内容必须带有适用对象、适用年龄、内容类型、来源、作者、版本、风险级别和商业标记。

### 8.2 推荐机制

推荐输入可以包括：

- 家长主动表达的问题；
- 家庭授权的当前目标；
- 内容收藏和反馈；
- 已完成或未完成的行动；
- 服务阶段；
- 年龄和适用范围；
- 明确的家庭偏好。

推荐输出必须能够解释“为什么出现”和“如何关闭”。未成年人的数据不能被用于自动化商业营销。孩子端若提供内容，应采用安全、适龄、低刺激、非商业化的产品模式。

### 8.3 创作者体系

创作者分为：

- 家庭经验创作者；
- 教师；
- 专业人员；
- 机构账号；
- 平台内容团队；
- 经过授权的合作伙伴。

“能发布内容”与“能提供专业服务”是两种不同资格。内容等级、服务资质和结算资格分别审核。

### 8.4 内容商业化

可采用：

- 会员内容；
- 付费课程或专题；
- 直播活动；
- 专业服务转化；
- 内容关联商品；
- 机构项目。

商业内容必须显著标识，不以隐性广告伪装成专业建议，不以孩子的敏感成长数据作为投放依据。

## 9. AI 与智能编排设计

### 9.1 AI 的五步工作链

```text
Context Assembly
→ Interpretation
→ Next Action Proposal
→ Resource Orchestration
→ Feedback and Evaluation
```

### 9.2 Context Assembly

AI 每次请求只读取当前任务必要的、已授权的最小上下文：

- 当前家庭和成员边界；
- 当前目的和同意；
- 当前成长需要和计划阶段；
- 相关证据和时间范围；
- 当前服务和订单状态；
- 适用的内容和供给范围；
- 必要的历史反馈。

Family Context 是跨域检索层，不是把所有数据复制到一个 AI 数据湖。原始权威事实仍归属各业务域。

### 9.3 输出层级

AI 输出必须带有：

- output_type；
- provenance；
- model/model_version；
- prompt_version；
- context_snapshot_ref；
- confidence 或不确定性说明；
- applicable_scope；
- safety_flags；
- human_gate_required；
- expires_at 或复核条件。

### 9.4 AI 与事实的隔离

AI 只能写入 AI Runtime 自己的草案、推理、追踪和评估记录，不能直接写入 Family、Growth、Service、Commerce 的权威事实表。

权威业务变化必须经过：

```text
AI Draft
→ 家庭或责任人查看
→ 人工/家长确认
→ 授权 Command
→ 业务域状态迁移
→ AuditEvent + OutboxEvent
```

### 9.5 Human Gate

Human Gate 不是“删除 AI 功能”，而是把 AI 建议接入责任链。以下动作至少需要显式确认或人工处理：

- 类诊断和高影响评估输出；
- 家庭计划重大变更；
- 教师、专家或服务推荐确认；
- 服务购买、会员升级和权益决定；
- 对外沟通；
- 涉及未成年人的敏感动作；
- 投诉、退款争议和供给方重大处置。

所有 gate decision 必须可追溯、可重放、可审计、可过期和可拒绝。

### 9.6 五个责任平面

AI 设计应同时覆盖五个平面：

1. 家庭事实面：Family、Assessment、Growth、Journey、Service、Commerce 的权威事实；
2. AI 控制面：Agent、Tool、Use Case、Prompt、Schema、Policy 和 Provider Admission；
3. AI 运行面：Context、Memory、Gateway、Safety、Evaluation、Trace 和 Cost；
4. 人工责任面：家庭确认、专业复核、运营审核、危机转人工和争议裁决；
5. 数据权利面：Consent、Read Audit、Retention、Deletion 和 Deletion Proof。

这五个平面不能被合并成一个“AI 服务表”。AI Runtime 负责运行和追溯，业务领域负责事实，人工责任面负责高影响决定，数据权利面负责处理合法性和可退出性。

### 9.7 Agent 角色和人机协作等级

同一个 AI 入口可以承载多个受控角色：

- 家长顾问：解释家庭问题和沟通建议；
- 孩子陪练：提供适龄练习和过程反馈；
- 助教助手：在授权案件内辅助教师和管家；
- 成长规划师：生成 21/90 天计划草案；
- 经营助手：提供运营、质量和成本洞察。

每个 Agent 需声明服务对象、上下文范围、工具、输出类型、风险级别、禁止输出和人工要求。

人机协作分为：

- `AI First`：普通解释、当前任务查询、非高影响提醒和格式化摘要；
- `AI + Human Assist`：人工辅助输入或复核上下文，但仍须记录 AI 最终输出和版本；
- `Human Lead + AI Support`：高影响判断、服务分派、计划变更、购买、对外沟通和敏感动作；
- `Immediate Handoff`：安全危机、疑似伤害、虐待或重大风险直接转人工，不等待普通队列。

“人辅助 AI 输入”不能冒充“人工复核决定”。

## 10. 数据、同意与信任设计

### 10.1 数据主体和权限

- 孩子是重要数据主体和成长受益者；
- 家长是主要授权和付款角色，但不是无限制读取所有信息的所有者；
- 家庭是服务和权限边界，不等同于数据所有权；
- 机构和供给方只获得目的限定的最小必要访问；
- AI 只有任务级、目的化和时间受限的读取权限。

### 10.2 数据分层

建议分为：

1. 权威业务事实：家庭、成员、同意、行动、服务、订单和权益；
2. 证据和过程记录：测评回答、行动记录、服务凭证、反馈和复盘；
3. AI 运行记录：草案、provenance、提示词版本、trace、cost 和评估；
4. 投影和检索索引：面向 UI、运营和 AI 查询的可重建派生数据；
5. 合成、sandbox 和测试数据：物理隔离的非生产数据。

派生向量、缓存、索引和快照必须支持按主体删除，不能把“无法删除向量”作为架构前提。

### 10.3 同意生命周期

```text
目的说明
→ 单独同意或拒绝
→ 可见授权范围
→ 使用和访问记录
→ 目的/范围变化重新同意
→ 撤回立即失效
→ 导出/更正/删除
→ 留存到期处理
```

同意不是一个全局开关。内容、测评、AI 个性化、专业服务、机构共享、商品推荐和社区分享应根据目的分别管理。

### 10.4 商业与未成年人

- 商业主体优先放在家长端；
- 不向未成年人进行自动化决策商业营销；
- 商品和服务推荐必须有家长确认和可拒绝路径；
- 未成年人消费控制、退款和权益失效必须有完整状态机；
- 不通过家庭成长数据制造焦虑性销售；
- 任何高风险推荐、敏感动作和数据共享保留人工复核。

### 10.5 家庭记忆和派生数据

家庭记忆分级管理：

- `M0` 会话记忆：当前对话、临时转写和媒体引用，短期保存，不自动进入长期记忆；
- `M1` 主动确认偏好：家庭明确确认的语言、节奏、可用时间和互动偏好，可查看、修改和删除；
- `M2` 成长上下文：评估证据、行动、服务交付和关系观察的授权投影；
- `M3` 长期学习特征：阶段性、脱敏后的模式和质量信号，默认关闭，启用前需 DPIA、删除演练和供应商审查。

记忆写入必须经过：

```text
MemoryCandidate
→ Consent
→ Family/Human Confirmation
→ MemoryItem
→ Authorized Retrieval
```

Embedding、摘要、缓存、ContextSnapshot 和评估副本继承原始数据的主体、目的、区域和可见范围。检索必须先过滤租户、家庭、主体、目的和同意，再执行向量近似搜索，并进行二次权限过滤和读取审计。

删除请求到达后，必须先用 Tombstone 阻断旧数据继续被检索，再级联删除原文、转写、摘要、向量、缓存、评估副本、训练副本和供应商副本，最终生成 `DeletionProof`。

### 10.6 内容推荐与家庭需要

内容推荐应采用：

```text
资格过滤
→ 候选生成
→ 安全/适龄过滤
→ 质量/相关性/多样性排序
→ 解释为什么推荐
→ 家庭反馈
→ 复盘评估
```

可使用已确认成长意图、当前家庭目的、内容适用年龄、语言、内容质量和家庭主动反馈。不能把停留时间、情绪脆弱状态、儿童行为偏差、消费能力推断作为唯一或主要依据。

每张推荐卡支持“不感兴趣、稍后查看、降低频率、暂停推荐、清空依据和转人工”。家长端可以在授权和主动需要基础上接收商品/服务推荐；儿童端不得接收基于画像的商品、会员、积分、拼团、返佣或广告推荐。

## 11. 服务网络与 FGCN 运营设计

### 11.1 供给准入

供给方准入至少包括：

- 身份和主体核验；
- 专业资质或服务能力证明；
- 服务范围和禁区；
- 未成年人保护培训；
- 价格、时段和容量；
- 服务协议和平台责任；
- 退款、争议和退出条件。

### 11.2 匹配规则

匹配不以抢单竞价为中心，优先考虑：

- 任务能力；
- 资质和风险级别；
- 服务连续性；
- 可用容量；
- 家庭偏好；
- 地域和语言；
- 历史履约质量；
- 利益冲突。

AI 可以给出候选排序，但高风险或重大分派需要责任人确认。

### 11.3 交付和结算

服务交付必须区分：

- 任务被分派；
- 任务开始；
- 任务完成声明；
- 交付证据提交；
- 家庭或责任人验收；
- 质量回访；
- 贡献确认；
- 结算释放。

分佣和结算不能依据孩子成长结果或未经证实的 AI 判断。应依据明确、可验收的交付贡献。

### 11.4 质量和争议

平台必须支持：

- 服务取消和改派；
- 超时和 SLA；
- 交付证据不足；
- 家庭不满意；
- 供给方申诉；
- 退款和部分退款；
- 责任认定；
- 服务恢复；
- 黑名单或资格暂停；
- 审计和复盘。

### 11.5 案件语义和多案件并存

“一客一案”不是指一个家庭一生只能有一个案件，而是指：一个已确认的家庭成长需要或一个已激活的服务计划，对应一个有独立目的、授权、蓝图和责任边界的 `ServiceCase`。

同一个家庭可以并行存在多个案件，例如学习习惯、亲子沟通和家庭活动案件，但每个案件必须独立记录：

- 目的和服务对象；
- consent 版本；
- GrowthIntent 或订单引用；
- ServiceBlueprintVersion 快照；
- 管家、任务和服务人员；
- SLA、交付证据和验收状态；
- 投诉、退款和结算关系。

案件之间可以通过家庭上下文和事件关联，但不能互相直接改写权威状态。一个案件结束、暂停或撤回，不应误伤家庭的其他合法案件。

### 11.6 资格与平台准入分离

供给方至少有两类不同事实：

- `QualificationStatus`：证书、专业资格、培训和有效期；
- `AdmissionStatus`：平台是否允许其提供某类服务。

证书过期、平台风控暂停、机构合同终止和单个项目容量关闭不是同一个状态，不能用一个 `active` 字段代替。准入状态至少应支持：

```text
APPLIED → SCREENING → QUALIFICATION_PENDING → REVIEWED → ADMITTED
→ ACTIVE → CAPACITY_LIMITED → SUSPENDED → RETIRED
```

高风险服务需增加人工审查、未成年人保护培训、服务边界、紧急升级和定期复核。

## 12. 机构与 B2B2C 设计

### 12.1 机构项目模型

机构合作建议抽象为：

```text
Organization
→ Contract
→ Program
→ EligibleFamilyScope
→ ConsentPolicy
→ DeliveryPlan
→ ServiceCases
→ AggregatedReport
→ Settlement
```

机构不能直接把任意家庭加入项目；家庭进入项目必须有合法来源和授权状态。

### 12.2 学校协同模型

学校或老师可以：

- 推荐资源；
- 提供课程或活动；
- 参与已授权的家庭计划；
- 查看任务范围内的反馈；
- 提交服务记录和建议。

学校或老师不能：

- 默认读取家庭全部成长上下文；
- 以孩子画像进行商业营销；
- 直接改变家庭权威事实；
- 绕过平台的服务、审计和争议机制。

### 12.3 机构报告

机构侧报告应优先输出：

- 项目覆盖率；
- 服务交付量；
- 行动完成趋势；
- 服务质量和满意度；
- 资源缺口；
- 脱敏聚合结果。

不能输出家庭排名、孩子排名或未经授权的个体画像。

### 12.4 B2B2C 合同和项目对象

B2B2C 至少拆成四类对象，不使用一个笼统的“机构用户”承载全部关系：

- `OrganizationAgreement`：平台与机构的主协议，约定主体、数据处理、责任、费用、内容、事故和退出；
- `ProgramOrder`：具体项目订单，约定服务产品版本、家庭范围、周期、容量、SLA、付款和结算；
- `FamilyActivation`：家庭对具体项目的激活、目的同意、参与方式、退出和投诉；
- `StaffAuthorization`：机构工作人员的项目、案件、字段和 Named Action 权限。

机构付费不等于家庭自动授权；家庭激活不等于机构取得家庭完整档案；工作人员离职或项目结束后，访问权必须立即收敛。

机构合作报告优先输出项目覆盖、交付量、行动完成趋势、质量和脱敏汇总，不输出未经授权的个体画像。

## 13. C2C 社区和家庭网络设计

### 13.1 社区核心循环

```text
家庭表达经验
→ 平台审核与范围设置
→ 其他家庭发现和互动
→ 共同活动或共同任务
→ 反馈与经验沉淀
→ 经授权进入内容/服务发现
```

### 13.2 互助和商业的边界

- 分享经验不等同于提供专业服务；
- 点赞和关注不等同于专业资格；
- 推荐不等同于平台担保；
- 家庭互助不自动形成返佣关系；
- 交易必须有平台订单、退款和争议入口；
- 家庭活动和低风险服务可以先进入受控目录；
- 高风险或面向未成年人的服务必须经过专业准入。

### 13.3 增长机制

可以使用：

- 家庭邀请；
- 共同活动；
- 家长同行计划；
- 内容分享；
- 经过审核的推荐奖励。

奖励应为单层、透明、封顶、与真实行为或服务贡献绑定，不能无限裂变，也不能把孩子作为传播和营销节点。

### 13.4 客户关系的五种分离

平台不能用一个“客户归属人”字段解决所有商业关系，至少要区分：

- `SourceReferral`：谁带来了家庭；
- `PlatformAccount`：谁向家庭提供平台服务；
- `ServiceSteward`：谁负责案件整体体验；
- `DeliveryProvider`：谁完成具体服务任务；
- `ProgramBuyer`：谁在 B2B2C 中付款或采购。

这五种关系可以属于不同主体，但家庭始终由平台承接和保护。家庭可以更换管家、老师、专家或机构，推荐人不能凭首次引荐取得永久客户所有权。

## 14. 平台技术架构

### 14.1 三进程和职责

```text
frontend/mobile / frontend/web
          ↓ HTTP Commands / Queries
family_api：事实、权限、同意、交易和业务域状态
          ↔ Port / Event / Query
ai_runtime：上下文、推理、Agent、工具、安全、Human Gate、评估
          ↔ Event / Workflow Port
workflow_worker：长流程、提醒、超时、重试、人工任务和补偿
          ↓
PostgreSQL / Redis / Object Storage / Vector Index / Outbox
```

AI Runtime 不直接写业务权威表。Workflow Worker 不绕过业务 Command 直接修改状态。

### 14.2 领域边界

目标领域包括：

- identity / tenancy；
- family / consent；
- content；
- assessment；
- growth / journey / action / outcome；
- program；
- service / FGCN；
- commerce / membership / entitlement；
- community；
- AI Runtime。

每个领域采用 `api / application / domain / infrastructure` 分层；跨域通过 Query Port、Command Port 或事件协作，禁止跨域直接 import repository。

### 14.3 数据和事件

每个权威状态变化至少携带：

- event_id；
- aggregate_type / aggregate_id；
- event_type / event_version；
- actor；
- tenant/family scope；
- correlation_id / causation_id；
- occurred_at；
- provenance；
- before/after 或明确的状态差异；
- audit_ref。

Outbox 负责可靠发布，Projection 负责可重建查询，Replay 不重新调用外部模型或支付供应商。

### 14.4 API 和命令规则

每个 API/Command 必须明确：

- 谁可以调用；
- 作用于哪个 tenant/family；
- 需要什么 purpose/consent；
- 需要什么幂等键；
- 前置状态；
- 成功输出；
- 拒绝和失败代码；
- 是否写事实；
- 是否发事件；
- 是否需要 Human Gate；
- 如何审计和回放。

推荐使用面向业务动作的命令，而不是让前端直接提交任意状态字段，例如 `ConfirmGrowthIntent`、`AcceptServiceDelivery`、`RequestRefund`、`ApproveHumanGateDecision`。

## 15. 测试环境与生产环境

### 15.1 必须相同

测试和生产必须使用相同的：

- 功能集合；
- API 和命令；
- 状态机；
- 权限和同意规则；
- AI 输出边界；
- 审计和 Human Gate；
- 订单、支付、退款、权益、积分和结算逻辑；
- 服务案件、任务、验收和争议流程；
- 社区审核和申诉流程。

### 15.2 允许不同

只允许替换：

- 商品和机构数据；
- 测试家庭和成员数据；
- 模型供应商或 sandbox provider；
- 支付、通知、短信和结算 adapter；
- 外部平台回调；
- 容量、密钥和部署规模。

### 15.3 测试数据规则

- 合成数据必须物理隔离并带来源标记；
- fake adapter 必须模拟成功、失败、超时、重复回调和退款；
- 不能用硬编码积分余额、订单金额或服务结果伪装成业务事实；
- 测试中必须验证生产同形状的拒绝、审计、回滚和补偿路径；
- 生产发布前不需要重新开发业务流程，只替换经过准入的真实适配器。

## 16. 运营和组织设计

### 16.1 家庭成功运营

负责：

- 家庭入营；
- 计划和行动陪跑；
- 服务升级；
- 续费和退出；
- 家庭反馈；
- 重大风险转人工。

### 16.2 内容运营

负责：

- 内容规划；
- 创作者和机构管理；
- 质量审核；
- 版权；
- 专题和直播；
- 商业标识；
- 内容风险和下架。

### 16.3 供给运营

负责：

- 老师、专家、机构准入；
- 服务目录；
- 时段和容量；
- 匹配质量；
- 交付证据；
- 质量抽检；
- 贡献和结算。

### 16.4 交易运营

负责：

- 商品和方案目录；
- 支付和退款；
- 会员和权益；
- 积分账本；
- 返佣和结算；
- 对账；
- 欺诈和异常交易。

### 16.5 信任与安全运营

负责：

- 未成年人安全；
- 内容审核；
- 数据权利；
- AI 安全和 Human Gate；
- 机构访问；
- 投诉和争议；
- 安全事件和年度审计。

### 16.6 AI 和数据运营

负责：

- Prompt、Schema 和知识版本；
- 模型路由和供应商准入；
- 评估集和回归；
- 输出质量；
- 成本和延迟；
- 追踪和审计；
- 删除、留存和派生数据清理。

### 16.7 平台责任模式

不同服务必须在产品、合同和订单中明确平台承担的责任强度：

- 平台运营型：平台设计、定价、收款、匹配、验收和售后，承担完整服务运营责任；
- 伙伴运营型：伙伴负责具体交付，平台负责准入、目录、订单、质量和争议，不能用“信息平台”规避实际控制责任；
- B2B2C 项目型：机构采购、家庭受益、平台交付，合同明确付款、授权、服务、安全、退款和退出后的连续服务责任。

平台实际控制了哪个环节，就必须对那个环节保留记录、质量标准和人工接管能力。

## 17. 指标体系

### 17.1 北极星指标

建议北极星指标为：

> 每周完成至少一次经家庭确认、可回读、可复盘的有效行动的活跃家庭数。

它比 DAU、播放时长、点赞数或家庭排名更符合平台定位。

- 家庭问题表达率；

- 同意完成率；
- 测评完成率；
- 假设理解和确认率；
- 首次行动启动率；
- 行动完成率；
- 服务转化率；
- 复盘完成率；
- 会员转化和续费率；
- 家庭主动退出率。

### 17.3 供给和服务

- 供给准入通过率；
- 有效容量；
- 匹配成功率；
- 预约完成率；
- 取消和改派率；
- 任务按时完成率；
- 证据完整率；
- 家庭验收率；
- 质量投诉率；
- 争议恢复时长；
- 供给方留存和贡献质量。

### 17.4 商业

- 家庭年度收入；
- 会员转化率；
- 会员续费率；
- 服务收入占比；
- 交易成功率；

### 17.5 信任和质量

- 高风险动作拦截率；
- 同意撤回生效时延；
- 数据删除完成率；

- 申诉处理时长；
- 关键事件审计完整率；
- 生产/测试行为差异数。

平台不把家庭排名、孩子排名、播放时长和焦虑性转化作为核心经营指标。

## 18. 分阶段建设路线

### Phase 0：统一合同和治理

目标：建立平台可以持续开发的共同语言。

交付：

- Family、Person、Role、Consent、Tenant 合同；
- Fact/Perspective/Hypothesis/Recommendation/Action/Outcome 边界；
- API/Command/Event 命名和幂等规则；
- 内容、服务、商品、订单和权益对象契约；
- Human Gate 和 Audit 契约；
- 测试/生产环境等价检查；
- Domain、Migration、AI 用例登记。

验收：同一业务动作可以明确归属域、输入、输出、状态、权限、审计和回放路径。

### Phase 1：家庭进入与内容到行动

目标：打通第一条 B2C 主闭环。

```text
内容/测评入口 → 家庭建立 → 同意 → 测评 → 假设解释 → 家庭确认 → 今日行动 → 复盘
```

验收：成功、拒绝、撤回、重复提交、过期和人工升级全路径可测；测试环境使用合成数据但功能完整。

### Phase 2：21/90 天计划与家庭协同

目标：让家庭从单次体验进入持续行动。

交付：GrowthIntent、PrimaryContradiction、JourneyPlan、JourneyPhase、Action、Outcome、FamilyReview。

验收：计划创建、暂停、恢复、变更、完成、失败和复盘具有明确责任和审计。

### Phase 3：专业服务和 FGCN

目标：建立主要付费交付能力。

交付：供给准入、服务目录、预约、案件、任务、交付证据、验收、质量、争议和贡献结算。

验收：一客一案、一任务一责任人、交付凭证、人工接管、退款/争议和结算闭环通过。

### Phase 4：会员、商品和权益

目标：把服务关系扩展为家庭方案和家庭消费。

交付：目录、方案、订单、支付、退款、会员、权益、积分账本、返佣、结算和售后。

验收：测试环境完整模拟真实支付与外部副作用；无硬编码资产；退款会反向失效权益和积分。

### Phase 5：B2B2C 机构网络

目标：引入学校、机构、社区和企业家庭福利。

交付：机构租户、合同、项目、家庭纳入、授权、服务项目、聚合报告和结算。

验收：机构数据最小化、家庭撤回、合同终止、权限收敛、项目级审计和聚合输出通过。

### Phase 6：C2C 家庭网络和内容增长

目标：形成家庭之间的信任和网络效应。

交付：社区、群组、活动、家庭分享、举报、审核、申诉、撤回、邀请和受控激励。

验收：内容安全、隐私范围、未成年人保护、单层封顶激励和争议处置通过。

### Phase 7：Family Context、Growth Graph 和智能编排

目标：形成难以复制的长期家庭成长能力。

交付：跨域最小上下文、时间序列证据、主要矛盾判断、干预策略、服务蓝图库、评估和个性化反馈。

验收：可解释、可回放、可删除、可人工接管；AI 不绕过业务域、不直写事实、不让模型供应商成为业务依赖。

以上阶段是商业验证和生产放大顺序，不是测试环境功能删减顺序。每个阶段进入开发后，允许的功能都必须按生产形状完整建设。

## 19. 必须坚持的设计决策

1. 孩子是价值中心，家庭是服务和商业单元；
2. 教育是入口，家庭成长和家庭关系是主业务；
3. B2C 是根，B2B2C 是放大器，C2C 是网络层；
4. 内容必须能够转成家庭行动，不能只追求消费时长；
5. AI 是理解和编排中枢，不是业务事实所有者；
6. 服务必须经过任务化交付、证据、验收和结算；
7. 商品必须从家庭需要进入，不能让商城反向制造需求；
8. 家庭数据归家庭控制，服务关系不等于数据所有权；
9. 不做家庭总分、家庭排名和以孩子为对象的自动化商业营销；
10. 测试环境和生产环境功能等价，只替换数据与外部副作用；
11. 任何“暂缓上线”的能力，都不应被误读为“测试环境不建设”；
12. 设计过不等于已经实现，所有成熟度必须由代码、测试和运行证据说明。

## 20. 需要继续裁决的事项

- 主要矛盾的最小数据契约和评估方法；
- 内容推荐的年龄、目的和商业隔离策略；
- 学校/机构数据接口的字段级最小化协议；

- 返佣、贡献结算、退款和争议的详细财务规则；
- C2C 活动、家庭互助和受控交易的风险分级；
- 真实支付、通知、机构和模型供应商的生产准入；
- DPIA、年度审计和未成年人数据删除的机制化落地；
- 当前仓库中各领域从目标设计到实现证据的逐项核销。

## 21. 完成定义

本总体设计从工作稿升为可执行基线，至少需要满足：

- 所有核心对象都有唯一领域归属；
- S01-S24/O01-O14 可映射到产品、流程和 API/Command；
- B2C、B2B2C、C2C 的付款、授权、服务责任和数据边界没有混淆；
- 内容、AI、行动、服务、商品、社区和数据权利形成端到端状态链；
- 每个高影响动作都有 Human Gate、Audit、拒绝和回放路径；
- 测试环境可以使用模拟数据完整走完生产形状的成功和失败流程；
- 关键商业指标来自权威业务事实，而不是 UI 点击、意向或硬编码值；
- 当前实现状态与目标设计逐项标明，不把“迁移进来”写成“能力已经存在”；
- 需要改变现有架构边界的决策已有独立 ADR；
- 通过产品、业务、工程、合规、运营和项目负责人的联合评审。
