# 家庭成长平台会员关系与贡献经济建设蓝图

> 本文是 AiFamily 的目标态业务规格和敏捷建设指挥文案，不是当前实现证明。
> 它专门补充 `docs/02_business/FAMILY_GROWTH_PLATFORM_MASTER_DESIGN_V1.md`，不与
> `docs/00_system/CURRENT_SYSTEM_BASELINE.md` 竞争现状真相。凡本文写“平台应当具备”的能力，
> 必须以代码、测试、审计证据和环境等价验收后才能从 Planned 进入 Implemented。

## 0. 一句话总纲

**以孩子为价值圆心，以家庭为服务和商业圆圈，以 AI 为理解、陪伴、编排和协作中枢，连接学校、老师、专业人员、机构、社区与家庭产品，帮助家庭看见需要、采取行动、获得真实帮助、彼此贡献，并在可信关系中持续成长。**

教育是切入口，不是终点；会员是长期关系，不是功能锁；积分是贡献记录，不是诱导消费的筹码；FGCN 是受治理的协作与履约网络，不是开放式专家市场；商业扩展必须建立在真实需要、成人授权、可验收交付和可追溯结算之上。

## 1. 这不是教育 App，而是家庭成长关系平台

### 1.1 价值对象与商业对象

平台同时处理三种不同对象，不能混成一个“用户画像”或一个“客户分数”：

| 对象 | 定义 | 平台责任 |
|---|---|---|
| 孩子 | 成长价值中心和被服务的受益主体 | 提供安全、适龄、可表达、非商业化的成长体验 |
| 家庭 | 关系、授权、服务和持续复盘的基本单元 | 维护共同目标、成员边界、权益和家庭选择 |
| 成人供给者 | 家长贡献者、教师、专业人员、机构和运营者 | 按资质、权限、交付和质量规则参与服务与结算 |

孩子是圆心，不等于孩子是商业流量节点；家庭是圆圈，不等于平台可以无限采集家庭隐私；家长是通常的付款人和主要授权人，不等于可以无条件查看或控制孩子的全部表达。

### 1.2 北极星与价值链

平台的北极星不是播放时长、广告点击、家庭总分或家庭排名，而是：

> **在授权和安全边界内，越来越多家庭完成了真实、可解释、可复盘、对关系有帮助的成长行动，并能在需要时获得可靠的产品、服务和互助资源。**

```text
家庭表达/孩子成长信号
  → 需求澄清与确认
  → AI 多模态理解与方案草案
  → 家庭选择和人工复核
  → 行动、产品、服务或 FGCN 协作
  → 交付证据与质量验收
  → 成长复盘、贡献确认和权益兑现
  → 新需求回流与长期会员关系
```

这条链必须贯穿 B2C、B2B2C 和受控 C2C；任何只做流量、只做交易、只做内容消费而不形成真实帮助的功能，都不是平台核心能力。

## 2. 建设原则：能做的功能完整做，必须守的边界硬守

### 2.1 允许建设的完整能力

测试环境必须拥有与未来生产环境相同的路由、领域规则、状态机、权限、Consent、审计、幂等、人工闸门、退款、申诉、回滚、重试和恢复能力。测试数据可以是 `SYNTHETIC`，支付、通知、模型和结算可以是可审计的 fake/sandbox adapter，但不能因此删除业务节点或把异步流程改成“测试专用同步捷径”。

因此，会员购买、内容审核、家长贡献、成人结算、家庭互助、服务预约、交付验收、退款和积分逆转，都必须在测试环境按生产形状实现。

### 2.2 必须保留的硬边界

- 不计算、不存储、不暴露家庭总分和家庭排名。
- AI 只能产生 `Perspective`、`Recommendation`、`Draft` 或 `ActionProposal`；权威事实和高影响状态必须经过授权的 Named Action，必要时经过 Human Gate。
- 不向未成年人进行自动化决策商业营销；儿童端不展示基于画像的商品、会员、积分、拼团、返佣、广告或直播打赏推荐。
- 不以孩子的露脸、成绩、情绪、行为、社交曝光或成长结果作为商业收益条件。
- 不把家庭私有内容静默写入公共知识库、供给者档案或其他家庭的上下文。
- 不把“真实支付/真实机构/真实模型尚未接入”解释成“测试不实现该功能”。

这些边界不是产品阉割，而是平台的信任、合规和长期商业价值的基础；禁止行为在测试和生产都应统一拒绝、审计并保留可解释的处理结果。

## 3. 三种商业模式的统一分工

三种模式不是三套互相竞争的产品，而是一个家庭成长平台的三条经营通道。

### 3.1 B2C：家庭关系和现金流的根

B2C 直接服务家庭，建立第一方长期关系和可持续现金流：

- 免费基础层：家庭身份、安全、基本需求表达、数据权利和基础内容访问；
- 会员层：连续家庭上下文、AI 多模态陪伴、21 天行动、90 天计划、家庭复盘、成员协作、人工管家和优先服务；
- 增值层：真人服务、活动、家庭解决方案、合规商品与家庭生活服务；
- 家长贡献层：经审核的经验内容、活动组织、互助、翻译、社区治理和合资格服务交付。

B2C 的经营目标是“问题被看见、行动有帮助、关系变稳定、需要有去处”，不是一次性卖测评或无限延长停留时间。

### 3.2 B2B2C：机构渠道和规模放大器

学校、社区、企业家庭福利、托育/照护机构和专业服务组织可以成为渠道、服务组织或供给方，但家庭的授权、数据权利和服务选择不能被机构吞并。

机构合作必须明确：

- 机构服务哪个家庭、哪个目的、哪个区域和哪个期限；
- 机构可以看什么、不能看什么，谁审批、谁执行、谁负责；
- 机构提供的是品牌入口、活动、服务、场地、内容还是支付补贴；
- 家庭可以拒绝、退出、导出和删除哪些数据；
- 服务质量、投诉、改派、退款、资质失效和合作终止如何处理。

B2B2C 不得成为学校或雇主监控孩子、家长或员工家庭的隐形数据通道。机构数据接口必须遵循最小必要、租户隔离、用途限定和可撤销授权。

### 3.3 受控 C2C：家庭互助和关系网络

C2C 只在明确的身份、内容审核、家庭隐私、成人责任和平台治理下开放。优先建设：

- 家庭经验分享与共同创作；
- 成人组织的亲子活动、兴趣活动和邻里互助；
- 家长之间的经验答疑和资源交换；
- 经平台审核的成人志愿服务、翻译、陪伴和社区治理；
- 面向家庭的内容、活动、产品和服务推荐。

C2C 不等于任何人都能接触儿童，也不等于任何人都能自称专家。高风险心理、医疗、法律、财务、儿童保护事项必须进入合资格人员和人工流程；AI 可以辅助整理、检索、分流和起草，不能替代资质责任人。

## 4. 会员体系：经营长期关系，而不是锁定基本权利

### 4.1 会员的核心承诺

会员购买的是“持续被理解、被陪伴、被协助完成事情”的关系服务，主要包括：

1. 家庭成长上下文的连续保存和可控复用；
2. 文本、语音、图片、视频、文件和互动记录的多模态陪伴；
3. 21 天行动、90 天计划、年度节奏与阶段复盘；
4. 家庭成员协作、可见性配置和共同决定；
5. 人工管家、专业服务和活动的优先权或额度；
6. 内容、课程、工具、模板、活动和家庭商品权益；
7. 数据查看、导出、删除、授权、撤回和目的管理；
8. 经验证的家庭贡献记录、互助资格和社区参与权益。

基础安全、身份、Consent、数据权利、投诉和未成年人保护不能被会员付费锁死。会员只能增加服务范围、连续性、响应质量或可用额度，不能购买绕过规则的特权。

### 4.2 关系角色模型

同一个人可以在不同家庭或不同交易中承担不同角色，系统不能用一个 `user_type` 或一个“客户归属人”字段替代这些关系：

| 角色标识 | 业务含义 | 关键约束 |
|---|---|---|
| `Payer` | 实际付款人 | 付款不自动获得全部家庭数据查看权 |
| `Buyer` | 作出购买或订购决定的人 | 购买必须在授权主体和目的范围内 |
| `Guardian` | 对未成年人承担监护和授权责任的成人 | 监护权、授权范围和撤回必须可核验 |
| `Beneficiary` | 实际获得成长或服务利益的家庭成员 | 可以是孩子、家长或整个家庭，但不产生家庭总分 |
| `DataSubject` | 被处理数据对应的个人 | 拥有查看、更正、删除、撤回和转移等权利 |
| `Contributor` | 提交内容、互助、活动或服务贡献的人 | 贡献须审核、验收、反作弊和可逆转 |
| `Provider` | 提供产品、服务、知识或资源的主体 | 资质、范围、容量、SLA 和质量可追溯 |
| `SettlementRecipient` | 最终接收成人结算款的人或组织 | 必须是合资格成人/法人并通过结算与税务校验 |

系统对象还必须通过 `tenant_id`、`family_id`、`subject_ids`、`purpose`、`consent_version`、`data_class`、`provenance_ref` 和 `deletion_ref` 建立边界。跨租户、跨家庭和跨主体读取默认拒绝。

### 4.3 会员状态机

```text
PROPOSED
  → CHECKOUT_PENDING
  → ACTIVE
  → PAUSED
  → GRACE
  → EXPIRED

ACTIVE → CANCEL_REQUESTED → CANCELLED
ACTIVE → REFUND_PENDING → REFUNDED
ACTIVE → SUSPENDED（风控/合规/欠款，必须有原因和复核路径）
```

状态规则：

- 只有 `ACTIVE` 且在有效期内的权益才能被消费；
- 暂停、过期、退款和取消会影响未来权益，不抹掉历史订单、使用和审计事实；
- 退款必须反向处理未消耗权益及其关联积分/贡献奖励，已结算款进入可追溯的逆转或争议流程；
- 会员状态和权益状态分开建模，不能用一个余额字段代替；
- 会员升级、降级、续费和跨家庭转移均须经过授权、幂等、审计和冲突处理。

## 5. 四本账：把成长、贡献、权益和现金彻底分开

### 5.1 成长证据账 `Growth Evidence Ledger`

记录家庭行动、反馈、复盘、服务事实、家庭确认的结果和可见性，不计算家庭总分，不制造跨家庭排名，也不把孩子变成绩效指标。

核心事实示例：`ActionRecord`、`FamilyFeedback`、`DeliveryRecord`、`QualityDecision`、`OutcomeEvidence`。

AI 观察必须保留来源、目的、版本、解释和不确定性；AI 不能直接把观察写成家庭事实或疗效结论。

### 5.2 贡献账 `Contribution Ledger`

记录成年人或受治理组织对平台和家庭网络的可验证贡献，例如：

- 经审核的家庭经验内容；
- 组织或完成家庭活动；
- 完成合资格的服务任务；
- 翻译、无障碍、知识整理和社区治理；
- 经过验收的互助、陪伴、资源整理或问题解决；
- 对平台安全、质量和公共知识的有效贡献。

贡献不是孩子的成长结果，不是点赞数，不是曝光数，不是停留时长，不是家庭排名，也不是 AI 单独判断的“有用”。

贡献状态：

```text
SUBMITTED → REVIEWED → VERIFIED → HELD → RELEASED
                    └→ REJECTED
RELEASED → APPEAL → REVERSED（必要时）
```

其中 `VERIFIED` 表示交付或贡献已经满足验收条件；`HELD` 用于冷静期、退款窗口、争议窗口或反作弊检查；`RELEASED` 才能兑现平台积分、会员权益或成人结算依据。

### 5.3 会员权益账 `Membership Entitlement Ledger`

记录会员、权益、额度、有效期、使用、冻结、失效、退款和恢复，不与积分余额共用一个账户。

至少支持：

- 权益版本冻结和历史订单引用；
- 使用前授权和有效期检查；
- 取消、退款、过期、迁移和补发；
- 额度并发扣减和幂等；
- 家庭成员的受益资格与可见性；
- 账务对账与客服解释。

### 5.4 真实结算账 `Settlement Ledger`

记录成人创作者、教师、专业人员、机构和平台之间的应付、暂存、释放、退款、逆转、税务/发票和对账事实。

平台积分、FGCN 贡献单位和现金结算不是同一种资产：

- `PlatformPoint`：平台权益或贡献激励单位，不能宣传为现金或金融资产；
- `FGCNContributionUnit`：用于记录案件内资源贡献和分配依据，可按规则拆分，不代表现金；
- `SettlementAmount`：经过交付验收、政策校验和对账后的成人结算金额。

禁止通过一个 `balance`、一个 `commission` 或一个 `reward` 字段同时表达这三种资产。

## 6. 贡献经济：让“人人为我、我为人人”可持续而不异化

### 6.1 贡献的获得方式

家长可以通过审核后的家庭经验内容、活动组织、成人互助、社区治理、翻译、无障碍支持以及合资格专业服务获得积分、权益或成人结算。贡献者必须知道：贡献做了什么、如何验收、何时释放、如何申诉、何时逆转。

内容创作应优先给予内容权益、家庭会员权益、活动资格、服务抵扣或平台积分；涉及真实现金时，只面向合资格成人创作者/服务者，按真实交付、版权、质量和结算政策处理。

### 6.2 分配原则

- 单层、透明、可解释、可封顶；
- 以真实提交、审核、交付、验收和质量为依据；
- 不以儿童曝光、儿童画像、成长成绩、情绪变化或家庭排名为奖励依据；
- 不鼓励无限裂变、拉人头、强制分享和商业骚扰；
- 同一贡献不能重复计入多个奖励池；
- 撤回、退款、判定无效、版权争议和欺诈确认后，必须支持逆转但保留原始事实和审计链；
- 贡献者的收入预期、平台抽成、结算周期和扣回条件必须在提交前可见。

### 6.3 互助池和赞助池

平台可以建立三类池，但每类池必须独立记账、独立规则和独立审计：

1. `MutualAidPool`：家庭和成人贡献者共同投入，用于经审核的互助任务、活动和公共资源；
2. `SponsorshipPool`：企业、机构或平台投入，用于补贴符合条件的家庭服务，不以儿童画像做营销筛选；
3. `QualityRecoveryPool`：用于返工、改派、补交付、退款补偿和质量修复。

池内资金或权益不能被 AI 自行分配；分配必须有适用条件、责任人、审批、期限、结果证据和回收/补救路径。

## 7. 家长、孩子和内容分享的商业边界

### 7.1 家长可以赚钱，但收入来自成人可负责的贡献

可行路径包括：

- 经审核的家庭经验文章、短视频、音频、图文或工具模板；
- 成人主持的亲子活动、兴趣活动和社区活动；
- 合资格的课程、陪伴、咨询、翻译、内容制作或服务交付；
- 成人用户的合规推荐和单层邀请；
- 内容审核、社区治理、知识整理和无障碍服务。

每条内容都要记录作者、版权、适用对象、年龄范围、商业标识、来源、审核、版本、失效和投诉状态。平台可以借鉴短视频产品的创作工具、关注、话题、直播和分发体验，但不能把家庭成长异化为刷屏竞赛。

### 7.2 孩子可以表达和共同创作，但默认不是直接商业主体

孩子可以在家长和平台的保护下进行表达、创作、活动和成长记录，但默认规则是：

- 不因露脸、声音、成绩、行为、情绪、粉丝、点赞或曝光直接计价；
- 不直播打赏、不带货、不拉新返佣、不承担持续表演压力；
- 不根据儿童画像自动推荐商品、会员、积分、服务或广告；
- 儿童内容默认最小可见、可撤回、可删除，并提供监护人与孩子的适龄权利路径；
- 若未来设计儿童共同创作收益，必须另立年龄、监护、收益托管、版权、隐私、税务和退出方案，不能由本稿默认授权。

儿童端的游戏感来自探索、合作、成就故事、任务完成和关系改善，不来自消费、竞争、公开排名或商业转化。

## 8. FGCN：从家庭需求到可信交付的协作内核

FGCN 不是一个开放式专家市场，也不是一个把家庭交给算法撮合的流量池。它是平台内部可治理的“需求—资源—任务—交付—验收—贡献—结算”操作系统。

### 8.1 标准链路

```text
FamilyNeed
  → SolutionBlueprintVersion
  → ServiceCase
  → ServiceTask
  → AssignmentPlan
  → DeliveryRecord
  → QualityDecision
  → ContributionRecord
  → SettlementStatement
  → OutcomeEvidence / NextNeed
```

每个案件必须有独立目的、授权范围、责任人、蓝图版本、服务边界、SLA、风险级别、交付物、验收条件、投诉/改派/补救路径和审计关联。资源不足时返回可解释的 `RESOURCE_GAP`，不能伪造供给或承诺无法交付的结果。

### 8.2 FGCN 的适用领域

优先适用：家庭教育与成长计划、亲子沟通、兴趣体育艺术、家庭活动、照护和生活服务、学校/社区/企业家庭福利、家庭解决方案组合和受控家庭互助。

条件适用：心理、医疗、法律、财务和儿童保护。此类场景必须由合资格人员和人工流程负责，AI 只做解释、整理、分流、提示和候选方案。

不适合单独使用 FGCN 的场景：普通内容播放、一次性 AI 问答、简单商品订单、普通续费和轻量点赞。这些场景可以接入平台，但不能假装成服务交付或贡献事实。

### 8.3 FGCN 的最小不变量

- 未确认的需求不能变成已授权服务案件；
- 未授权或越权的人员不能查看家庭敏感上下文；
- 未准入、资质过期或容量不存在的供给者不能承接任务；
- 一个任务只能有一个当前责任人和一个明确交付状态；
- 未完成或未验收的任务不能释放贡献或现金结算；
- 一次贡献只能确认一次；重试、重复回调和重复验收必须幂等；
- 退款、撤回、投诉和争议不能抹掉原始交付和审计事实；
- AI 不能自动派单、自动验收、自动结算或自动关闭投诉；
- 任何失败都能进入重试、人工接管、改派、补交付、退款或申诉流程。

## 9. 产品、服务和解决方案的扩展路线

### 9.1 从教育入口扩展到家庭需要

平台产品目录按“家庭需要”组织，而不是按“课程库存”组织：

1. 教育与学习习惯：阅读、专注、作息、学习方法和家庭学习环境；
2. 家庭关系：沟通、冲突、规则协商、亲子共同活动和家庭会议；
3. 身心与生活方式：运动、睡眠、饮食、兴趣和日常节奏；
4. 照护与家庭支持：托育、照护、家政、出行和特殊时期支持；
5. 兴趣与社会连接：体育、艺术、自然、志愿活动和社区参与；
6. 家庭解决方案：组合产品、真人服务、活动、工具和阶段性陪伴。

医疗诊断、临床治疗、法律结论和财务决策不因被放进目录就降低风险等级；它们必须保留专业资格、人工确认和适当的外部责任边界。

### 9.2 三种供给形态

- `Product`：标准化、可复制、可定价的内容、工具、课程或权益包；
- `Service`：由真人或受治理 AI 协助完成的互动、陪伴、判断和补救过程；
- `Solution`：围绕一个已确认需求组合多个产品、服务和资源的版本化执行蓝图。

解决方案不是商品打包页。它必须冻结目标、适用/排除条件、参与角色、成本、SLA、风险、验收、失败补偿和版本引用。

## 10. 多模态与游戏化：极致体验服务于真实成长

### 10.1 多模态能力

平台应逐步支持文本、语音、图片、视频、文件、OCR、转写、情境卡、时间线和互动任务，但必须将三类对象分开：

- `MediaAsset`：原始语音、图片、视频或文件；
- `MediaTranscript`：经授权产生的转写、OCR 或结构化结果；
- `MediaEvidence`：在特定目的、主体和可见性下被家庭确认或引用的证据。

原始媒体不能因为“方便 AI”就无限期进入家庭上下文或公共知识库。每次处理都绑定目的、同意版本、保留期限、主体范围、来源和删除关联。

### 10.2 游戏感和成就感

可建设的正向机制：

- 家庭共同任务、亲子仪式、连续行动和阶段里程碑；
- 个人成长故事、徽章、收藏、主题空间和可分享成果；
- 贡献等级只描述已验证的贡献经历，不描述人的价值或家庭优劣；
- 合作挑战、互助任务、活动地图和家庭愿望清单；
- 由家庭选择的反馈、庆祝和复盘节奏。

禁止把成就系统做成家庭总分、跨家庭排名、孩子公开竞赛、消费排行榜或以连续在线时长换奖励。成就必须绑定事实证据、明确用途、可撤回、可解释，并且不能成为商业营销儿童的依据。

## 11. AI 在平台中的位置

AI 是家庭成长的理解和协作中枢，不是权威事实的拥有者，也不是商业状态的最终执行者。

### 11.1 建议的受治理能力

- `need_interpreter`：把家庭表达整理为可讨论的需求假设；
- `multimodal_companion`：在目的限定下处理文本、语音、图像和视频互动；
- `solution_architect`：组合产品、服务和资源形成方案草案；
- `resource_coordinator`：解释适配条件和资源缺口，不直接承诺派单；
- `service_guardian`：陪伴交付、发现风险、准备补救建议，不自行关闭投诉；
- `contribution_reviewer`：整理审核证据和风险，不独立释放现金或权益；
- `family_economy_assistant`：解释会员、权益、积分和退款事实，不暗示儿童购买。

每个 AI 用例必须有输入合同、输出 schema、上下文策略、数据级别、允许工具、人工闸门、Provenance、评估集和回滚策略。领域代码只能经 `backend/intelligence/model_gateway` 访问模型，AI 输出初始状态必须是 `DRAFT`/`PROPOSED`。

## 12. 数据、同意和信任底座

- Consent 按目的、主体、范围和版本管理，并同时提供拒绝、撤回、更正、删除和导出路径；
- 未成年人数据按敏感数据和最小必要原则处理，字段绑定目的、留存期限、到期处理和删除关联；
- 14 岁线用于敏感信息和产品默认体验设计，不能关闭未成年人或监护人的法定数据权利通道；
- 读取未成年人数据也要记录最小授权、访问目的、审批依据和访问字段；
- 派生的 embedding、缓存、索引、快照、转写和训练材料必须支持按主体删除；
- 外部模型、支付、消息和结算供应商必须经过数据处理、分包、删除、区域和安全审查；
- 公共内容只可复用经过授权、去标识化、许可清晰且不含家庭私密事实的材料；
- 所有高影响动作均需权限、Consent、Audit、Idempotency 和必要的 Human Gate。

## 13. 建设顺序：把宏大版图切成可以验收的纵向切片

以下是平台建设顺序，不是测试环境功能删减顺序。每一阶段一旦开工，测试环境就必须实现该阶段完整生产形状。

### P0：基础闭环和共享 WIP 收口

目标：完成 `FamilyNeed → Assessment → GrowthIntent → Onboarding → Action → Review` 的单家庭链路，解决现有 Onboarding 的 migration、挂载 contract、Ruff、PostgreSQL E2E、Consent 等价语义和重启回读问题。

退出条件：正向、越权、跨租户、未确认、Consent 撤回/失效、冲突幂等、审计失败回滚、worker 重启恢复和 HTTP E2E 全部有证据。

### P1：成人家庭贡献纵向切片

```text
成人家长提交经验内容
  → 内容/版权/安全审核
  → 成人家庭使用或报名
  → 贡献确认
  → PlatformPoint 或会员权益入账
  → 退款/撤回/申诉/逆转
  → Audit + Outbox + 对账回放
```

退出条件：Fake 仅替换外部支付/结算，领域规则、权限、审核、状态机和失败路径与生产一致；不能出现硬编码积分余额、自动确认贡献或儿童商业推荐。

### P2：会员、权益和家庭资产

落地会员生命周期、权益版本、家庭成员可见性、续费、暂停、退款、权益失效、数据权利和会员客服解释。先保证账本与状态正确，再扩充套餐和促销。

### P3：FGCN 交付和质量

落地 `SolutionBlueprintVersion → ServiceCase → ServiceTask → Delivery → Quality → Contribution → Settlement`，支持准入、匹配、改派、补交付、投诉、申诉、退款、质量池和结算回放。

### P4：受控 C2C 和家庭成长媒体

落地家庭经验分享、多模态创作、内容审核、关注、话题、活动、私密分享和成人创作者收益；孩子端使用安全、适龄、非商业化模式。

### P5：B2B2C 机构协作

落地机构租户、服务协议、最小数据接口、家庭授权、机构供给、质量复盘、合作终止和数据删除；使用合成机构数据做完整测试，不先接大规模真实数据接口。

### P6：家庭需要商品化和规模化

将已被真实交付验证的能力扩展为产品、服务和解决方案目录，接入支付 sandbox、真实结算前的对账、库存、售后和区域化运营。每次扩展都必须复用既有需求、交付、质量和贡献内核。

## 14. Agent 联合舰队的分工与工作协议

每个 Agent 只负责明确的文件范围和一条纵向证据链，不得整体暂存、格式化或提交其他 Agent 的 WIP。

### 14.1 角色编组

| 小组 | 负责范围 | 首要交付 |
|---|---|---|
| Journey/Family | Need、Assessment、GrowthIntent、Onboarding、Action、Review | P0 闭环和反向矩阵 |
| Membership/Entitlement | 会员生命周期、权益账、退款和可见性 | P2 纵向切片 |
| Contribution/Loyalty | 贡献账、积分、审核、申诉和逆转 | P1 纵向切片 |
| FGCN/Service | Blueprint、Case、Task、Delivery、Quality、Settlement | P3 纵向切片 |
| Experience/Multimodal | 家庭媒体、AI 陪伴、成就、游戏化和前端体验 | P4 合同与 E2E |
| Governance/Safety | Consent、Audit、AI Registry、数据删除、合规和反向挑战 | 全阶段质量门禁 |
| SRE/Database | migration、PostgreSQL、Outbox、重启、回滚和环境等价 | 每个切片的持久化证据 |

### 14.2 每个切片的强制交付包

1. 目标业务场景、输入、输出、参与者和结束条件；
2. Domain 聚合、不变量、Command、Event 和 Port；
3. Fake 与 PostgreSQL adapter，Fake 只替换外部依赖；
4. API contract、错误码、幂等键、审计和 Outbox；
5. 正向测试与反向测试；
6. 迁移、回滚、重启恢复和数据清理测试；
7. 目标文档、ADR（如涉及架构决策）、Domain/Capability/AI registry 同步；
8. 独立提交、测试命令、结果、已知缺口和下一步建议。

## 15. 每轮都要进行反向挑战

任何 Agent 回报“完成”前，必须由另一角色提出至少一个可能让方案失败的反例，并用测试或代码证据回答：

| 反向问题 | 必须证明什么 |
|---|---|
| 这是完整功能还是测试捷径？ | Fake/Postgres/HTTP 使用同一业务规则和状态机 |
| 未授权的人能不能看到或改变数据？ | 跨租户、跨家庭、跨主体、AI actor 均 fail closed |
| 撤回、过期、退款和删除之后会不会继续生效？ | 权益、Consent、缓存、embedding、积分和结算均反向处理 |
| 重试、并发和重复回调会不会重复入账？ | Idempotency、唯一约束、Outbox 和回放测试 |
| AI 是否越过了事实、商业或人工闸门？ | 输出状态、Named Action、Human Gate 和 Provenance 证据 |
| 贡献是否被孩子曝光或成长结果驱动？ | 奖励因果链只指向成人贡献和验收事实 |
| 资源不足时是否伪造供给？ | 返回 `RESOURCE_GAP`，没有虚构 provider、容量或交付 |
| 退款/争议是否抹掉了事实？ | 原始订单、交付、审核和审计保留，生成逆转事实 |
| 测试数据是否误挂生产？ | `SYNTHETIC` 隔离、生产路由检查和环境等价报告 |

## 16. 验收指标：衡量真实帮助、信任和可持续经济

### 16.1 家庭价值

- 需求澄清完成率和家庭主动确认率；
- 计划启动率、行动完成率和复盘完成率；
- 家庭反馈的“有帮助/需改进/未解决”分布；
- 服务按时交付率、返工率、投诉解决时长和改派成功率；
- 家庭主动续费、主动扩展和主动推荐，而不是被打扰后的点击。

### 16.2 贡献与商业

- `VERIFIED` 贡献占提交贡献的比例；
- 贡献争议率、逆转率、重复奖励率和结算准确率；
- 会员激活、有效使用、续费、退款和权益兑现率；
- 真实交付带来的服务收入、成人创作者收入和机构合作收入；
- 平台补贴/质量池对返工和家庭救济的覆盖情况。

### 16.3 信任与安全

- 未授权读取/写入拦截率；
- Consent 撤回后的失效时延；
- 删除请求覆盖原始数据、派生数据、缓存和索引的完成率；
- AI 高风险输出进入人工复核的覆盖率；
- 儿童商业推荐、家庭排名、家庭总分和 AI 直写事实的零容忍违规数。

### 16.4 工程与环境等价

- 同一业务验收套件在 Fake、PostgreSQL 和 HTTP 层的一致结果；
- migration 链、回滚、重启回读和 outbox 回放通过率；
- 架构测试、Ruff、contract test 和全量测试结果；
- 每个已声明能力都有代码、测试、文档、registry 和指标证据。

## 17. 本文对平台建设的直接命令

1. 先闭合家庭需求到行动的真实链路，再把会员和贡献接到真实事实；
2. 先建设四本账和状态机，再做积分商城、促销、返佣和创作者收益的 UI 放大；
3. 先做成人贡献和受控家庭互助，再考虑任何儿童共同创作收益；
4. 先做 FGCN 的准入、任务、交付、验收和争议，再扩大专家、机构和家庭资源网络；
5. 先用多模态提升理解、陪伴、表达和复盘，再把游戏化用于合作成就，不用于焦虑竞争；
6. 先建立数据目的、Consent、删除、审计和人工闸门，再扩大上下文和推荐范围；
7. 每一项能力都在测试环境完整实现，生产只替换数据与外部适配器，不允许“测试版阉割”；
8. 每一个 Agent 都必须接受另一 Agent 的反向挑战，未通过证据门禁不得宣称完成；
9. 每个切片独立提交、可回滚、可追责；禁止把并发 WIP 混入提交；
10. 所有商业增长都必须回答一个问题：它是在帮助家庭更好地生活和成长，还是在利用孩子和家庭的不安赚钱？只有前者进入平台。

## 18. 当前状态声明

本文提出的是目标态业务规格。按照当前系统基线，会员、贡献、FGCN、B2B2C、受控 C2C、家庭成长媒体和完整商业结算仍需按上述阶段逐步落地；“文档已写”不等于“能力已存在”。每次状态晋升必须由实现路径、测试证据、架构门禁、数据/合规审查和可回滚方案共同证明。
