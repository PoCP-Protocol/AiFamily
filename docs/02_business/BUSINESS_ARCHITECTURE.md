## 0. 本文件的性质

本文件不重新设计商业模式。三份原始战略材料（V1.1实施方案、白皮书、新商业模式PPT）已经把商业模式讲清楚，V2战略已经用34个UI的真实代码审计核实过这套商业模式哪些环节是真的、哪些只是PPT愿景。本文件做的事是把这些已经确认的判断，按"业务架构"的方式组织起来：顶层定位是什么、经营对象是什么、业务对象的第一约束是什么、钱从哪里来、靠什么机制协作、底线原则是什么。

每一条判断标注来源章节/页码，不新增没有来源的商业概念。

## 1. 顶层业务定位

### 1.1 一句话号召："家是港湾，孩子是希望"

来源：V2战略第0.1节，项目负责人在本次会话确认，作为整份战略的"为什么"。

21天挑战计划、90天成长营表面是服务交付产品，但围绕的核心从来不是"课程"或"测评分数"，而是三件事：**孩子的成长、家庭教育方式、家庭关系本身**。目标是构建一种新型的、和谐的家庭关系——家庭内部的关系，也包括家庭与家庭之间的关系。

这句号召不是营销口号，是产品设计的价值筛选器：任何新功能/新产品/新服务都要反问——*这是在帮助家庭变得更和谐、更有力量，还是在制造焦虑、贩卖排名、把孩子变成绩效指标？* 第4节的六项战略原则、宪章R9（不做家庭总分/排名）都是这个定位在治理层面的具体化，不是外部强加的合规负担。

### 1.2 公司定位："家庭成长数据科技公司"，不是AI工具公司也不是传统教培公司

来源：白皮书Slide 1/7。

- **不是**传统课程公司，不靠老师个人能力无限扩张（摆脱人效天花板）；
- **也不是**AI聊天工具公司，不把大模型包装成唯一卖点（避免技术同质化）；
- **而是**家庭成长产品、数据和AI协同的平台公司（形成长期复利）。

新商业模式PPT Slide 1把这条定位表达为公式：**孩子问题是入口 × 父母二次成长是价值 × 家庭改变是结果**。Slide 2把战略问题总结为"经营对象从一次成交的课程客户，变为持续成长的家庭用户；核心资产从课程/讲师/销售团队，变为用户/数据/案例/社区/生态；最终定位从家庭教育培训公司，变为中国父母成长生态平台"。

### 1.3 经营对象：不是单门课程，是家庭持续出现的成长需要

来源：V1.1第1.2节"最终定位"。

- **经营对象**：不是单门课程，而是一个家庭在不同阶段持续出现的成长需要。
- **核心产品**：不是内容包，而是"测评—诊断—方案—行动—陪伴—复盘—复购"闭环。
- **核心能力**：用AI承接高频标准服务，用管家保证连续性，用专业资源处理个性化和风险问题。
- **核心网络**：家庭只面对Family，后台资源按任务进入，交付完成后退出。
- **核心壁垒**：家庭成长数据、服务蓝图、贡献凭证、质量信用和跨机构协作规则。

这一条与V2战略"三区方法论"（第8节）互相呼应：独占区候选（Family Context/Family Growth Graph/Growth Intervention Engine/Service Blueprint Library）正是"经营家庭成长需要"这个定位在技术上的具体投射，不是并列的技术选型。

## 2. 核心业务对象的第一约束：Fact ≠ Perspective ≠ Recommendation ≠ Action ≠ Outcome

这不是技术架构约束，是**商业模式的差异化护城河**。

来源：白皮书Slide 15原话表达的克制态度（"AI应该放在交付闭环里，而不是放在品牌第一句里"），及V2战略第4节明确定性：

> 这六条与Family Coding Constitution的核心原则（`Perspective≠Fact`/`Hypothesis≠Fact`/`Recommendation≠Decision`/不做总分/不做排名）是同一个价值取向的商业表达——**不是合规负担，是差异化商业壁垒**：市面上多数教育App用"分数排名"制造焦虑变现，Family坚持"不诊断不打分"却依然能让家长感受到专业和陪伴，这个信任感本身就是护城河，一旦为了短期转化率妥协就跟其他平台没有区别，护城河也就不存在了。

工程侧的可执行定义见 `governance/REPOSITORY_CONSTITUTION.md` R9：

| 层 | 定义 | 谁能写入 |
|---|---|---|
| Fact | 家庭权威事实（relationship/consent/lifestage 等真实状态） | 只能经 Named Action 写入 |
| Perspective | AI或人对 Fact 的推断/解读 | AI 可生成，永不自动升格为 Fact |
| Recommendation | 基于 Perspective 给出的建议 | AI 可生成，仍不是 Fact |
| Action | 唯一改变权威状态的写入动作 | 必须经过审计（R6） |
| Outcome | Action 执行后产生的结果记录 | 与"打卡"等历史概念不可等同 |

从FELS（旧世界参考实现）继承的否定语义表（R9原文）是这条约束的反面教材证据：

| 旧世界对象 | 迁移规则 | 红线 |
|---|---|---|
| `legacy_profile.family_score` | RETIRE | 永不入 Family / 非 GrowthState |
| `legacy_profile.ranking` | RETIRE | 永不入 Family / 无家庭排行 |
| `legacy_checkin` | TRANSFORM | 打卡 ≠ GrowthActionCompletionFact ≠ Outcome |
| `legacy_tag.*` | LEGACY_ANNOTATION | 非永久人格标签 / 非诊断 |
| `legacy_ai_report.ai_conclusion` | HISTORICAL_AI_HYPOTHESIS | 非 Fact / 非诊断 / 非疗效承诺 |
| `legacy_assessment_score.score` | HISTORICAL_EVIDENCE | 非 GrowthState |
| `legacy_advisor_note.note_text` | PERSPECTIVE | 非 Fact |
| `legacy_alert.risk_score` | SAFETY_SIGNAL_SOURCE | 非阈值 / 非自动动作；高风险须 Human Gate |

**AiFamily 不计算、不存储、不暴露家庭总分与家庭排行**——这条约束贯穿本文件后续所有商业设计，任何新收入结构、新产品阶梯的设计都不得绕过它。

## 4. FGCN（家庭成长协作网络）机制

来源：V1.1第二章（贝壳ACN机制的借鉴与Family改造）+ V2战略第5节明确"保留、不重写"。

### 4.1 机制来源与改造原因

贝壳ACN（Agent Cooperate Network）在公开文件中被描述为一套标准协议：将复杂交易拆成多个步骤，明确角色、权责和佣金分配，使跨店、跨品牌合作成为可执行的日常机制；贝壳ESG报告强调按贡献分配、规则治理、监督机制和争议裁决共同构成底线管理（V1.1第2.1节，附录C引用来源1/2）。

Family借鉴的不是十个经纪角色，而是"把复杂家庭服务拆成可验收任务，让资源共享有边界、分工协作有凭证、价值分配有规则、争议处理有人负责"这个核心洞察（V1.1第2.2节"Family可借鉴的本质"）。

### 4.2 FGCN定义与六条运行规则

FGCN（Family Growth Collaboration Network，家庭成长协作网络）是嵌入Family平台的服务协作内核，不是独立的大型交易市场，而是一套用来配置分工、调度资源、记录贡献、控制访问、保障质量并形成分配依据的运行机制（V1.1第2.3节）：

1. **一客一案**：每个明确成长需要进入一个 ServiceCase。
2. **一案一管家**：每个案件只有一个有效 ServiceSteward，对家庭体验负责。
3. **一任务一责任人**：同一时刻只有一个被接受的任务责任人。
4. **一次交付一凭证**：完成、验收、返工与质量反馈均有不可篡改记录。
5. **一个案件一次分配**：案件总池为100个贡献单位，不能每验收一个任务再复制100。
6. **配置先于执行**：已发布蓝图不可修改，案件启动时冻结版本快照。

这六条不是抽象口号，V1.1第七章给出了对应的核心运行对象与状态机：`ServiceBlueprintVersion(DRAFT→REVIEWED→PUBLISHED→RETIRED) → ServiceCase → ServiceTask(PENDING→OFFERED→ACCEPTED→IN_PROGRESS→DELIVERED→VERIFIED) → TaskAssignment → ServiceContribution → AllocationStatement`，是第一阶段必须跑通的主链。

### 4.3 Family与贝壳机制的边界（不照搬清单）

V1.1附录B明确列出五条边界，是FGCN"改造"而非"移植"的证据：

| 贝壳 | Family |
|---|---|
| 最小协作单元是交易角色 | 最小协作单元是服务任务 |
| 以成交形成佣金 | 以已验收服务贡献形成分配依据 |
| 强调房源与客源共享 | 只共享经授权的最小必要上下文 |
| 以跨店跨品牌提高效率 | 以跨教师、机构、内容和专家提高服务完整性 |
| 用陪审团处理利益争议 | 先由运营和独立质量负责人处理，规模后建立伦理与争议治理 |

V1.1第2.4节及附录B还明确列出"不照搬"的具体做法（固定十角色→核心模型只认资源槽位和任务；抢客抢单竞价→系统按资格/能力/连续性/容量/家庭偏好匹配；客户归属→推荐人和教师不拥有家庭；成交即分完→交付验收确认基础贡献质量池在回访后释放；无限层级裂变→只允许监护人账户的一次性/单层/封顶激励；自动黑箱裁决→AI只给建议，重要分派/验收/退款/申诉由人确认）。

### 4.4 B2C / B2B2C / C2C 三种模式定位

来源：V2战略第3节，本次会话新增的显性命名（V1.1原文没有用这套语言，但设计内容已隐含）。

| 模式 | 对应层 | 现状 | 是否需要新设计 |
|---|---|---|---|
| **B2C** | 层1+层2（AI自服务层+人机协作层，UI-02~24核心闭环） | 生产商业验证优先；测试环境和生产功能集合必须相同 | 不需要新增模式，继续补齐完整测试路径和真实交付证据 |
| **B2B2C** | 层3的机构侧 | 测试环境完整实现机构租户、项目、家庭授权、交付和聚合输出；生产按真实机构准入放大 | 不需要新增模式，补齐 API、权限、Consent、Audit、E2E 和真实机构适配器 |
| **C2C** | 层3的社区侧（家庭间互助/经验分享） | 测试环境完整实现发布、审核、互动、举报和申诉；生产按社区安全与用户准入放大 | 不需要新增模式，**不是**"独立教师/顾问直接对家庭开店接单"的自由市场模式——那与V1.1第1.4节"客户由平台服务，不归属任何教师、机构或推荐人"直接冲突，明确不采用 |

三层价值网络（AI自服务层/人机协作层/生态放大层）的完整展开，及每层对应的真实完成度证据，见 `BUSINESS_SCENARIOS_AND_PROCESSES.md` 第2节。

本节的层级表示商业验证与生产规模化顺序，不表示测试环境功能范围。未被法律或产品边界明确禁止的能力，必须在测试环境用合成数据、sandbox 或 fake adapter 完整实现；生产发布只替换真实数据和获准的外部依赖。明确禁止的正向行为则在所有环境保留相同的拒绝、审计和人工处理路径。该解释遵循 `docs/10_engineering/ENVIRONMENT_PARITY.md` 与 ADR-0020。

## 5. 六项战略原则（V1.1第1.4节，V2战略第4节确认未被推翻）

以下六条来自V1.1第1.4节，V2战略核实后确认与当前Python-only架构或已验证代码现实不存在冲突，继续作为商业战略底线：

1. **家庭拥有家庭数据**；服务关系不等于数据所有权。
2. **客户由平台服务**，不归属于任何教师、机构或推荐人。
3. **服务分工按任务配置**，收入分配按已验收贡献确认。
4. **成长结果用于改进方案**，不直接作为个人扣罚或分佣依据。
5. **AI可以建议、生成和协助，但高风险分派、验收与权益决定必须由人负责。**
6. **当前采用轻内核完成真实纵向切片**；允许的业务流程在测试环境先以完整状态机、工作流和模拟外部适配器验证，生产接入真实数据和真实结算后，再按规模拆系统、扩角色和自动化运营。

第5条是AI架构侧的直接治理红线，在 `AI_ARCHITECTURE.md` 第4节展开为具体的工程约束（Draft/Hypothesis/Proposal，不得直写canonical状态）。

这六条与第2节的四层区分是**同一个价值取向的商业表达**（V2战略第4节），不是两套互相独立的原则。

## 6. 三区方法论——比三层价值网络更根本的一层判断

来源：V2战略第8节，项目负责人本次会话提出，采纳为上位方法论。

三层价值网络（第3、4节）回答"钱从哪里来、按什么节奏做"；三区方法论回答一个更根本的问题：**为什么别人抄不走**。

| 区域 | 本质 | 竞争状态 | 对Family的意义 |
|---|---|---|---|
| **同质区** | 市面上大家都有、门槛低、容易复制 | 充分竞争，利润率低 | 必须有，不能没有，但不能成为战略投入重点 |
| **优势区** | 别人也能做，但Family做得明显更好 | 有竞争但有差异 | 中期价值转化点，值得投入把"更好"做扎实 |
| **独占区** | 只有Family能做，且随家庭数量和服务时长增长越来越难复制 | 竞争弱，高粘性 | 长期护城河，是唯一值得押注核心研发资源的地方 |

判断一项能力属于哪个区，看的不是功能本身多先进，而是背后有没有一串别人短期无法复制的东西撑着：独有数据+独有算法+独有流程+独有服务网络+长期客户关系+持续学习机制+品牌信任——单一技术组件（比如"接了某个大模型API"）从来不构成独占。

**当前分类**（基于已完成的技术现状调研，非空想）：

- **同质区**：通用AI问答、AI生成育儿类文章、普通打卡、通用内容推荐。
- **优势区**：21/90天真人+AI协同计划、专家咨询预约网络（FGCN机制）——唯一端到端验证过的付费闭环，护城河程度中等（理论上有资源的竞争对手可以复制这套协同机制）。
- **独占区候选**（目前基本是空白，恰恰因此才最值得投入）：Family Context、Family Growth Graph、Growth Intervention Engine、Service Blueprint Library——四项技术现状均已确认是骨架/意图层面而非实际运行，具体证据见 `AI_ARCHITECTURE.md` 第3、4节。

这个方法论的排期结论：接下来的核心研发资源应该向四个独占区候选倾斜，不是因为技术新颖，而是因为"现在最空白的地方，恰好是理论上最高利润、最难复制的地方"（V2战略8.2节）。

## 7. 分级流程架构

业务架构不仅描述业务定位、能力和价值链，还必须给出流程架构的层级边界。本节规定“业务流程如何从商业价值落到可执行动作”；节点级输入、活动、输出和规则继续由 `BUSINESS_SCENARIO_CLOSURE_CATALOG.md` 维护，数据对象和事件由 `BUSINESS_SCENARIO_DATA_ARCHITECTURE.md` 维护。

### 7.1 六级流程层次

```text
L0 价值流（Value Stream）
 └─ L1 端到端流程组（End-to-End Process Group）
     └─ L2 业务场景（S01-S24）/平台运营场景（O01-O14）
         └─ L3 子流程（Sub-process）
             └─ L4 流程节点/活动（Node/Activity）
                 └─ L5 系统操作（API、Command、Event、Job、Human Task）
```

| 层级 | 回答的问题 | 设计产物 | 本项目的唯一标识 |
|---|---|---|---|
| L0 价值流 | 为谁创造什么可交付价值 | 价值流、起点、终点、结果 | `VS-01`～`VS-05` |
| L1 流程组 | 哪些端到端流程共同完成价值流 | 主流程、责任域、输入/输出边界 | `P01`～`P06` |
| L2 场景 | 哪一个业务或运营闭环 | 触发、角色、成功/拒绝、完成度 | `S01`～`S24`、`O01`～`O14` |
| L3 子流程 | 场景内部哪一段可独立复用 | 子流程状态、前置、异常分支 | `Pxx.1`、`Pxx.2` |
| L4 节点 | 一步具体做什么 | 输入、活动、输出、规则 | `Sxx-Nyy`、`Oxx-Nyy` |
| L5 系统操作 | 如何由系统或人员执行 | API/Command/Event/Job/Human Task、幂等、审计 | 端点、Named Action、事件名 |

L0-L2 是业务架构的稳定层；L3-L5 可以随实现演进，但不得改变 L2 场景的业务边界。任何新增功能必须先挂到一个 L2 场景，再设计 L3-L5，不允许直接从 UI 或数据库表反推业务流程。

### 7.2 L0 价值流（对应商业蓝图五个支柱）

| 价值流 | 价值承诺 | 起点 | 终点 | 主场景 |
|---|---|---|---|---|
| `VS-01 家庭成长交付` | 从家庭问题进入到可确认的成长行动/成果 | 内容、活动或测评入口 | 计划执行、复盘、年度沉淀 | S01-S09 |
| `VS-02 服务协作交付` | 按任务调度专业资源并完成可验收服务 | 已确认成长需要 | 交付验收、质量恢复、贡献凭证 | S10-S14、S23 |
| `VS-03 商业关系增长` | 以透明交易和长期权益维持家庭关系 | 商品/方案意向 | 会员使用、续购、资产回读 | S15-S18 |
| `VS-04 家庭关系与信任` | 让家庭分享、互动和数据权利可控 | 社区发布或数据请求 | 审核处置、删除/导出、安全闭环 | S19-S20 |
| `VS-05 平台经营与能力进化` | 让内容、AI、伙伴、组织和运营可持续 | 运营事件、市场信号或治理事项 | 指标决策、模型/版本发布、组织治理 | S21-S24、O01-O14 |

### 7.3 L1 端到端流程组与 L2 场景归属

每个 S/O 场景有一个**主归属流程组**；跨流程能力通过“横切控制”引用，不重复创建第二个事实源。

| L1 | 端到端流程组 | L2 业务场景 | 主平台运营场景 | 结束条件 |
|---|---|---|---|---|
| `P01` | 家庭触达、身份与入营 | S01-S03 | O01、O03、O04 | 家庭边界、成员角色、目的同意和入口来源可追溯 |
| `P02` | 测评、假设、计划与行动 | S04-S09 | O02 | 测评证据冻结，家庭确认意图，计划/行动完成或明确暂停/升级 |
| `P03` | 陪跑、专业服务与 FGCN 交付 | S10-S14、S23 | O05、O06、O07 | 服务记录、验收、质量/争议和伙伴责任完成 |
| `P04` | 商品、会员、资产与关系增长 | S15-S18 | O08、O09 | 订单/支付/权益/积分/邀请事实完成或明确失败/退款 |
| `P05` | 社区、数据权利与安全信任 | S19-S20 | O10、O11 | 内容审核/申诉或权利请求/安全事件完成并留痕 |
| `P06` | 运营、AI、指标、发布与组织治理 | S21-S22、S24 | O12、O13、O14 | 运营决策、AI 评估、版本发布或治理事项形成可审计结论 |

横切关系：`O04` 影响 P01/P02/P04 的家庭生命周期，`O12` 影响 P02/P06 的 AI 产物，`O14` 影响全部 P01-P06 的发布、审计和事故处理；这些是复用关系，不改变主归属。

### 7.5 L4/L5 节点到系统实现的落地规则

L4 节点的权威定义在场景目录中；L5 只能实现节点，不能创造新的业务语义：

| L5 类型 | 责任 | 必须携带 |
|---|---|---|
| API/Command | 接收用户/运营意图，调用聚合方法 | actor、tenant/family、purpose、consent、idempotency |
| Domain Policy/State Transition | 校验前置、状态迁移、拒绝条件 | 版本、权限、状态机、业务错误码 |
| Event/Outbox | 发布跨域事实和副作用请求 | event_id、aggregate、correlation/causation、provenance |
| Projection/Query | 面向 UI、运营和报表读取 | 来源事件、可重放、字段脱敏、不可写事实 |
| Job/Workflow | 重试、超时、补偿、提醒和留存作业 | retry、deadline、补偿、死信、审计 |
| Human Task | 复核、验收、投诉、风险和治理决策 | reviewer、decision、reason、before/after、时间 |

任何 L4 节点都必须能回答：谁触发、前置状态是什么、失败如何退出、输出写入哪个权威域、事件如何重放、运营如何接管。没有这些信息的 UI 按钮或数据库字段不能算作流程能力。

## 9. 与应用架构的衔接

业务架构只定义价值、流程边界和场景语义；应用架构负责把这些场景编排成用例、接口、工作流和运行组件。两者按以下关系对齐：

```text
VS/L0 → Application A0
P/L1  → Application A1/A2
S/O/L2 → Application A3 Use Case
L3    → Application A4 Workflow/Human Gate/Job
L4    → Application A5 Command/Query Contract
L5    → Application A6 Router/Handler/Repository/Event/Projection
```

应用架构的唯一设计文件为 `docs/06_platform/APPLICATION_ARCHITECTURE.md`。应用层不得增加新的业务场景、事实类型或数据表；发现 UI、接口和流程不一致时，应先修正本文件与数据架构，再改应用实现。

本轮裁决：`S16 会员方案、权益激活与年度续购` 的主归属为 `P04/VS-03`；它可以作为 VS-01 的服务支撑，但不再作为 VS-01 主场景，避免应用层出现双写入者和重复闭环。
- `BUSINESS_SCENARIOS_AND_PROCESSES.md`：保留已核实的六类业务闭环、FGCN 机制和功能完成度；`BUSINESS_SCENARIO_CLOSURE_CATALOG.md` 进一步补齐 24 个业务场景与 14 个平台运营场景的节点契约。
- `docs/07_data/BUSINESS_SCENARIO_DATA_ARCHITECTURE.md`：将本节 L2-L5 流程节点映射到权威聚合、事件和 Projection；流程层级不允许脱离数据事实单独演进。
