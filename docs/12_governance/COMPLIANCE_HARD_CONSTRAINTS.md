## 0. 为什么这份文件是硬约束而非建议

AiFamily 的核心数据主体是**家庭与未成年人**，这使它落入中国法规密度最高的数据场景之一。经对抗性核验（每条声明3票独立验证，2/3推翻即淘汰），以下条款被逐字确认，且**处罚梯度中"责令暂停或终止提供服务"在第一档即可适用**——不以"拒不改正"或"情节严重"为前提（PIPL第66条）。

即：**下架风险是前置的，不是累犯后果。**

这份文件的每一条都改变架构，不是加一段免责声明能满足的。

## 1. 「成长画像」不是同意就能做（最重要的一条）

**法源**：PIPL 第28条——敏感个人信息"包括…以及不满十四周岁未成年人的个人信息。只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下…方可处理。"

关键结构（核验确认）：
- "以及"置于"等信息"之后，属**无条件的类别性纳入**——14岁以下未成年人的**全部**个人信息都是敏感信息，不需要逐项判断是否敏感。
- 必要性检验在第28条；监护人同意义务在第31条。**两者累加，不可互替。** 拿到监护人同意 ≠ 通过必要性检验。
- 第4条把"存储"纳入"处理"，因此**留存期限直接受必要性检验约束**。
- 第6条"最小范围、不得过度收集"是**不可由同意豁免**的底线。

### 架构含义

白皮书 Slide 19 的三层画像设计（父母画像/孩子画像/家庭画像，含"情绪状态""行为变化""冲突类型"）**不能按"先全量采集、以后再想用途"的数据湖模式实现**。

进一步，《儿童个人信息网络保护规定》第12条（存储期限不超过实现目的所必需）+ 第13条（加密等措施存储）+ 第14条（用途扩展须再次取得监护人同意）+ 第11条（不得收集与服务无关信息）+ 第10条（须**事前**披露存储期限与到期处理方式）构成闭环：**用途未定的无限期留存无法满足第10条的事前披露义务**。

因此 `DATA_ARCHITECTURE.md` 中 Family Context / Family Growth Graph 的设计必须：
1. 每个字段绑定**声明过的具体目的**，而非"用于AI个性化"这种笼统表述；
2. 每个字段有**明示的留存期限**与到期处理方式，且该期限在采集时就已告知监护人；
3. 目的变更 → 触发重新同意流程，不能静默复用；
4. 加密存储（第13条"加密等措施"中加密为示例，非唯一合规控制，但是最低门槛）。

## 2. AI 评估输出 = 自动化决策（触发可解释/可拒绝/人工复核/DPIA）

**法源**：PIPL 第73条第2项定义自动化决策为"通过计算机程序自动分析、评估个人的行为习惯、兴趣爱好或者经济、健康、信用状况等，并进行决策的活动"——涵盖基于儿童行为/健康信号的评估。

第24条第3款逐字："个人有权要求…予以说明，并有权拒绝…**仅**通过自动化决策的方式作出决定"。

**"仅"字是承重限定**：合规解法是**提供人工复核路径与可退出选项**，而不是取消模型输出。这一点与 AI 原生定位不冲突——AI 仍是主路径，但必须有人工通道。

第55条：**"处理敏感个人信息"与"利用个人信息自动化决策"两项分别独立触发**事前个人信息保护影响评估（DPIA）；第56条要求报告与记录**至少留存三年**。AiFamily 两项同时成立。

### 架构含义

这一条与宪章 R9（AI输出不得自动成为事实）和 `AI_NATIVE_PRINCIPLES.md` 高度同构，但增加了两项此前未覆盖的**法定工程义务**：

1. **可解释性是法定要求，不只是产品体验**：每个 AI 评估输出必须能回答"为什么得出这个判断"，这要求 provenance 记录 model/model_version/prompt_version/context_snapshot/confidence 是**强制**而非最佳实践。
2. **DPIA 记录留存 ≥3年**：需要真实的评估文档与记录机制，不是一次性文档。

保守解读建议：第73条定义要求"**并进行决策**"，纯描述性报告是否构成"决策"及是否具"重大影响"属事实判断。**按保守解读设计**——即假定我们的评估输出构成自动化决策，配齐可解释+可拒绝+人工复核，而不是论证自己不适用。

## 3. 绝对禁止：向未成年人做自动化决策商业营销

**法源**：《未成年人网络保护条例》第24条第3款——"不得**通过自动化决策方式向未成年人进行商业营销**"。核验确认这是**绝对禁止型条款，无例外、无年龄细分**（适用全部未成年人，不限14岁以下）。

罚则（第55条）：责令改正、警告、没收违法所得、可并处10万元以下罚款；拒不改正或情节严重可责令暂停业务、停产停业、吊销许可证或营业执照；违法所得100万元以上者并处1-10倍罚款。

### 架构含义（直接否决一项商业设计）

新商业模式 PPT 的积分商城、会员权益、成长拼团等设计，**不得基于成长画像向孩子端推送**。这不是"要谨慎"，是绝对禁止。

- **孩子端**：禁止任何基于画像/行为数据的商业推荐。
- **家长端**：不受本条禁止，**但仍受 PIPL 第24条第2款约束**——须提供非个性化选项或便捷拒绝方式。

这与源仓库 UI-17（积分商城，`GATE_BOUNDARY` 状态，含 `pointsBalance ?? 1280` 硬编码兜底值）的现状形成呼应：该页面此前被产品边界拦住是**正确的**，且现在有了明确法源依据。

**核验纠正的一处误解**：家长端并非完全豁免，PIPL 第24条第2款与第55条影响评估义务仍适用。

## 4. 消费限额：在线教育未被列举，但不可依赖此漏洞

**法源**：条例第44条要求合理限制不同年龄阶段未成年人的单次与单日累计消费额，"不得向未成年人提供与其民事行为能力不符的付费服务"。

服务类型列举为网络游戏/直播/音视频/社交，**未列入在线教育**。同一四项列举在第43条（未成年人模式）、第45条（应援集资）重复出现，说明是刻意界定而非漏列。

**但**：第44条列举含"等"字，监管可类推适用；且第28条要求"以未成年人为服务对象的在线教育"按年龄阶段特点提供相应产品与服务。

### 架构含义

若 AiFamily 名义服务对象是**家长**，可能落在第28条之外——但**设计上不宜过度依赖这一点**。商业化（Batch 6 COMMERCE 闭环）应主动实现消费限额能力，而不是论证自己不适用。该闭环应在测试环境按生产形状完整建设并验证消费限额、权限、Consent、Audit 和失败路径；生产阶段只切换真实数据与获准外部适配器。

## 5. 同意流程：禁止一次性打包勾选

**法源**：《儿童个人信息网络保护规定》第9条（告知+监护人同意）、第10条（**同时提供拒绝选项** + 七项告知，含存储地点/期限/到期处理方式、拒绝后果、更正删除途径；末段：告知事项发生实质性变化须再次取得同意）、第14条（超出约定目的范围须再次同意）、第8条（专门规则+专人负责）。

反打包的最强法条实为 **PIPL 第29条"单独同意"** 与第14条第2款（目的/方式/种类变更须重新取得同意），宜并引。

注：第10条第(七)项为兜底项，"七项"是列举计数而非七项实质披露。

### 架构含义

`backend/platform/consent/` 的 Wave 1 实现需要扩展以支持：
- **按目的（purpose）分别授权**，而非一个总开关（现有 `ConsentPurpose` 枚举方向正确）；
- 同意界面必须**同时提供拒绝选项**；
- 目的/范围变更触发**重新同意**，不能静默继承；
- 撤回后立即失效（Wave 1 已实现无缓存的 `ConsentGate.check`，方向正确）。

## 6. 删除权覆盖向量与派生数据（对 AI 架构的实质约束）

**法源**：《儿童个人信息网络保护规定》第19条（更正权）、第20条（删除权，四项触发："包括但不限于"监护人撤回同意/终止使用服务/超出目的范围或必要期限/违法违约处理）、第23条（停止运营须立即停止收集并删除全部儿童个人信息）。

第28条仅豁免"无法识别为儿童个人信息"的自动留存数据。

**核验的关键推论**：按孩子维度派生的**画像向量 / embedding 仍属可识别儿童个人信息**，落入第20条删除对象。

### 架构含义（这条最容易被工程忽略）

**向量库与模型派生数据的清除是真实法定义务，不是"尽力而为"。**

因此 `DATA_ARCHITECTURE.md` 中 Family Context 的向量化设计必须从第一天就支持**按 subject 维度的级联删除**：
- 原始数据删除 → 对应 embedding 必须同步删除；
- 不能采用"向量不可删只能重建整个索引"的方案，或必须有可接受的重建机制；
- 注销级联删除要覆盖所有派生存储（缓存、索引、快照、训练集）。

这直接影响向量方案选型——pgvector 的行级删除能力在这一点上优于某些只支持批量重建的方案。

## 7. 委托第三方处理：不得转委托（对 LLM 供应商选型的硬约束）

**法源**：《儿童个人信息网络保护规定》第16条——委托第三方处理须**先做安全评估**、签委托协议、受托方**不得超出授权范围**、**不得转委托**、委托关系解除时及时删除；第17条：向第三方转移另须自行或委托专业机构做安全评估。

### 架构含义（可能是最难满足的一条）

调用外部 LLM / 向量服务属"委托第三方处理"。**"不得转委托"对架构有实质约束：多数 LLM 厂商在第三方云上再分包。**

这意味着：
1. Model Gateway 的供应商准入必须包含**合规审查维度**，不只是技术可用性——这扩展了宪章 R7 的意义（收敛供应商调用不只是工程整洁，是合规前提）；
2. 需要评估各供应商的分包结构，可能限制可选供应商范围；
3. 涉及未成年人数据的推理请求，可能需要**数据脱敏后再出境/出域**，或选择可承诺不转委托的部署形态（私有化/专属实例）；
4. 委托关系解除时的删除义务需要供应商侧配合承诺。

**此条需要法务与商务介入**，不是纯技术决定。列为待办。

## 8. 内部访问控制与年度审计是法定强制工程义务

**法源**：《未成年人网络保护条例》第36条（工作人员访问未成年人个人信息须**最小授权**、经负责人或授权管理人员**审批**、**记录访问情况**并采取技术措施）、第37条（**每年**自行或委托专业机构做合规审计并及时报告网信等部门）。

两条均用"应当"，第37条明示"每年"，**无规模阈值或豁免**，监护人同意不豁免。

### 架构含义

- `backend/platform/authorization/` 需支持最小授权模型（Wave 1 的 fail-closed PolicyEngine 方向正确）；
- `backend/platform/audit/` 的访问留痕不只覆盖"状态变更"（宪章 R6），还必须覆盖**读取访问**——这是对 R6 的扩展。**T-07 已补结构层**：`AuditActionKind.READ` + 第36条四要素 + `AuditRecorder.record_read()`，且"未成年人读取无审批"在构造期即被拒；业务路径级检查待首个真实读取路径落地（见 §11 第3项）；
- "逐次审批"是保守解读，基于角色的预授权 + 逐次访问日志亦可争辩合规；
- 年度合规审计需要机制化，不是一次性文档。

## 9. 14岁分界线的正确适用范围（纠正一个常见误解）

**核验推翻了三条错误归因**（0-3票），正确表述如下：

- 14岁分界线来自 **PIPL 第28条**（敏感信息）与**第31条**（监护人同意+专门处理规则），**不是**来自《未成年人网络保护条例》。条例全文"十四周岁"**零命中**。
- 条例第34条赋予"未成年人**或者**其监护人"**并列的**查阅/复制/更正/补充/删除权（含数据转移途径），**不以14岁分界**；第33条框定监护人角色为引导未成年人行使自身权利；第四章（31-38条）零处年龄引用。
- PIPL 全文"监护人"仅出现1次（第31条）；第44/45条的知情权/查阅复制权授予"个人"而**无监护人代行条款**——故 **PIPL 本身不赋予家长查看14岁以上孩子数据的权利**。

### 架构含义

**14岁应用于"同意采集"与"家长监视型UI默认值"，不得用于关闭14-17岁段监护人的数据请求通道。**

这与源仓库既有的"14岁隐私线"设计需要重新校准：
- 14岁以下：全部信息为敏感信息，监护人同意 + 必要性检验；
- 14-17岁：不再自动属敏感信息类别，但监护人与未成年人**并列**享有数据权利，不能因为过了14岁就切断监护人通道；
- 家长查看孩子隐私内容的**产品默认值**可以按14岁分界（这是产品选择，且符合"反监控促倾诉"的产品理念），但**法定数据请求通道**不能关。

条例中年龄仅以相对表述"不同年龄阶段"出现于第28条（在线教育适龄）、43条（未成年人模式）、44条（消费限额）、47条（游戏适龄提示）。

## 10. 执法风险梯度（量化）

**法源**：PIPL 第66条，含"或者"的择一表述（非"从高"）。

| 档位 | 后果 |
|---|---|
| 一般违法 | 责令改正、警告、没收违法所得，**并对违法处理个人信息的应用程序"责令暂停或者终止提供服务"** |
| 拒不改正 | 并处 100万元以下罚款；责任人员 1-10万元 |
| 情节严重（省级以上部门） | 并处 5000万元以下 或 上一年度营业额 5% 以下；可责令暂停业务/停业整顿；通报吊销许可证或营业执照；责任人员 10-100万元，**并可被禁止在一定期限内担任董监高及个人信息保护负责人** |

**关键设计含义**：**"责令暂停或者终止提供服务"在第一档即可适用**，不以"拒不改正"或"情节严重"为前提——**下架风险前置**。严重档的暂停业务/吊销为"可以"（裁量），且吊销经"通报有关主管部门"实施。

**本轮局限**：未能检索到具体行政处罚/下架案例，此项仅为法定罚则梯度，非实际执法强度证据。

## 11. 待办与未决

1. **第7条（不得转委托）需法务与商务介入**评估 LLM 供应商分包结构，可能限制供应商范围或要求私有化部署。
2. **DPIA 机制化**：第55/56条要求的影响评估报告与记录留存≥3年，需要建立流程，不是一次性文档。
   → **设计方案已出**：`DPIA_MECHANISM_DESIGN.md`（T-07，`status: draft`，落地需先出 ADR）。核心判断：DPIA 绑定"处理活动"而非代码提交；六个触发器 T1–T6 各有可判定的代码信号；评估报告存 `governance/DPIA/*.yaml`（git 历史即三年不可篡改留存），处理记录存审计表。**尚未落地**——前置依赖是首个真实未成年人数据处理活动的出现。
3. **读取访问日志**：宪章 R6 当前只覆盖状态变更，需按条例第36条扩展到读取访问留痕。
   → **结构层已落地**（T-07）：`AuditEvent` 新增 `AuditActionKind`（MUTATION / READ）判别式 + 第36条四要素（`subject_person_id` / `accessed_fields` / `access_purpose` / `approval_ref`），并把"读取未成年人数据而无审批"变成**构造期即失败**的不变量；`AuditRecorder.record_read()` 是唯一读取留痕入口。三个架构检查器守此结构（见 `tests/architecture/test_compliance_constraints.py` 的第36条小节）。
   → **仍缺业务路径级检查**（"每条读取未成年人数据的代码路径都真的调用了 record_read"）。当前四个业务域（assessment / membership / product_intelligence / loyalty_points）均无未成年人主体读取路径，写这条检查器会检查空集并永远通过，故按 R14 精神明确推迟到首个真实读取路径落地时补。
4. **留存期限绑定**：每个存储未成年人数据的字段须有明示留存期限、到期处理方式与声明过的具体目的（第10/12条）。
   → **设计方案已出**：`DATA_RETENTION_BINDING_DESIGN.md`（T-07，`status: draft`）。核心判断：字段级元数据（pydantic `json_schema_extra` / SQLAlchemy `mapped_column(info=)`，五键必填）+ 反射检查器；采纳"按模块范围 opt-out + 全局命名启发式兜底"（方案 C），并如实记录其残余缺口（字段名不含主体 token 时静态检查拦不住）。**尚未落地**——同样等首个真实数据模型。
5. **年度合规审计**：第37条法定义务，需机制化。
6. **未检索到执法案例**：本轮 deep-research 未找到具体处罚/下架案例，实际执法强度未知。建议后续补一轮针对"教育类/儿童类App 处罚与下架案例"的定向研究。
7. **14岁线设计校准**：需要逐个 UI/端点复核现有"14岁隐私线"实现是否误用于关闭监护人法定数据通道。

## 12. 与商业战略的冲突记录（如实标注，不回避）

| 商业设计 | 来源 | 合规状态 |
|---|---|---|
| 积分商城/会员权益向孩子端推送 | 新商业模式PPT | **绝对禁止**（条例第24条第3款），必须改为仅家长端且提供非个性化选项 |
| 三层画像长期沉淀（"越用越懂家庭"） | 白皮书 Slide 18/19 | **受限**：须逐字段绑定目的+留存期限+事前披露，不可数据湖式全量留存 |
| AI 诊断/成长报告展示给家长 | 白皮书 Slide 12/17 | **允许但须配套**：可解释+可拒绝+人工复核路径+DPIA（保守解读） |
| 家庭总分/家庭排名 | 无（宪章R9已禁） | 与合规同向，双重禁止 |
| 会员积分体系 | 白皮书 Slide 8 | 家长端可行；孩子端禁止自动化营销；须考虑消费限额（第44条类推风险） |

**结论**：商业战略的核心叙事（测评→诊断→方案→行动→陪伴→复盘→复购）在合规上是可行的，但**孩子端商业化路径被实质关闭**，增长设计必须以家长为商业主体。这一点白皮书"父母二次成长是价值"的定位反而是有利的——它天然把商业关系放在家长侧。
