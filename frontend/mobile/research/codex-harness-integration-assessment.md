> **结论：可以融入。** 推荐将 Codex Harness 首先作为 **Family AI 的开发协作层**，而不是直接放进 iOS/Android App 或让其读写家庭业务本体。首个试点应锁定在隔离工作树中的 **UI-05 原图对齐与自动验证**，仅使用测试数据、限定文件范围、允许运行检查和测试，禁止网络副作用、推送、合并及真实家庭数据访问。

## 1. 现状与判断依据

Family AI 已具备一个清晰的单核心系统：Expo 移动端是主要用户入口，NestJS Family API 是家庭范围内投影和受控命令的唯一业务入口。移动端通过 Bearer token、家庭上下文、幂等键和请求快照访问 API；成长计划、任务和服务等业务不应被第二套代理逻辑复制。当前本地环境中未安装 Codex CLI，也不存在名为 `codex` 的现成连接配置，因此本轮只完成接入设计，不安装、不授权、不启动代理服务。

Codex 的开源 Harness 可管理线程、上下文、工具调用、沙箱策略与审批；官方将其定位为由宿主应用掌握业务上下文、业务规则与工具，而 Harness 负责代理执行循环。[1] [2] 这与 Family AI 的“一个核心系统、移动端不重建业务逻辑”原则相容：**Family AI 必须继续拥有家庭数据、政策、审计和最终写入权；Codex 只在被赋予的受限工作区内协助开发与验证。**

## 2. 可选接入路径

| 方式 | 如何融入 Family AI | 适合内容 | 代价与限制 | 建议 |
|---|---|---|---|---|
| **受控本地开发协作** | 在隔离 Git 工作树中通过命令行运行单次任务；输出改动、测试记录和差异报告 | UI 原图对齐、类型/测试修复、契约补充、代码审阅 | 需安装 CLI 并以 ChatGPT 账号或 API 凭据授权；任务结束即退出 | **首选试点** |
| **CI/研发任务执行器** | 针对拉取请求或明确任务启动短生命周期代理，回传结构化测试、差异和建议 | 回归测试、文档巡检、限定重构、PR 预审 | 需为每次执行隔离代码与密钥，不能自动合并或发布 | 第二阶段 |
| **产品内协作面板** | 由服务端驱动 App Server，向管理端展示代理进度、批准请求和改动产物 | 研发运营工作台，不面向家庭用户的编码任务 | 需要长期进程、会话持久化、事件流、凭据托管和专门审批界面 | 仅在前两层稳定后评估 |

官方将一次性或 CI 型受限工作推荐为 `codex exec`，将程序化控制推荐为 SDK，将持续会话、事件流和审批推荐为 App Server。[1] App Server 的协议是双向 JSON-RPC/JSONL，可把工具调用、差异和批准请求作为可观察事件返回给宿主；这适合未来的研发工作台，但不是移动端业务功能的直接依赖。[2]

## 3. Family AI 的目标架构

```text
产品用户
  └─ Expo iOS / Android App
       └─ NestJS Family API ── PostgreSQL
            ├─ 家庭范围授权、投影、受控命令、审计与幂等
            └─ 既有模型网关（仅限明确的产品能力）

研发人员 / 经批准的研发任务
  └─ Family AI 开发控制面
       ├─ 任务规格：原图、路由、允许文件、验收命令、禁止项
       ├─ 隔离 Git 工作树 + synthetic/dev 数据
       ├─ Codex Harness（CLI 单次任务 → 后续可升级 App Server）
       └─ 结果：diff、测试、截图/替代证据、审计记录、人工审批
```

该结构将 Codex 放在 **研发控制面**。它不获得移动客户端中的 API key，不直接读取生产数据库，不直接调用家庭范围命令，也不替代既有产品模型网关。任何未来从研发控制面进入业务系统的写入，都仍须通过现有 NestJS policy、Named Action、审计和幂等边界。

## 4. 必须编码的控制边界

| 边界 | 受控规则 |
|---|---|
| **数据** | 首个试点仅挂载版本化源码、legacy UI 原图、原始页面函数、测试与 synthetic/dev fixture；不得挂载真实家庭记录、令牌、生产数据库导出或 `.env`。 |
| **文件写入** | 以隔离工作树执行；任务声明允许修改的文件清单；任何迁移、API 合同、数据架构变化都需单独任务与审批。 |
| **命令执行** | 白名单为 `pnpm check`、`pnpm test`、`pnpm lint`、受限截图或静态分析；禁止安装未审查的系统包、删除目录、访问外部生产系统。 |
| **Git 与交付** | 代理可以生成 diff、提交候选和测试产物；不得自行推送、创建/合并 PR、发布或回滚。以上动作由明确批准的人工或既有受控流程执行。 |
| **产品语义** | 不允许代理将 Reflection 当 Fact、生成儿童诊断、家庭排名、总分或效果结论；不允许绕过 Model Gateway、Ontology Adapter 或 Named Action。 |
| **审计** | 每次运行记录任务 ID、基线 commit、输入资产哈希、允许文件、命令、退出码、改动摘要、测试结果与人工批准决定。 |

## 5. 推荐首个试点：UI-05 原图对齐代理任务

**目标。** 让 Codex 在一个独立工作树中协助完成下一页 UI-05 的“先看原图、列差异、再修复”的重复研发环节；它不决定功能范围，范围由已恢复的 UI-05 原图和原始页面函数共同限定。

| 项目 | 试点约束 |
|---|---|
| 任务输入 | `delivery-community-reference-458x1128.png`、`coreCommunity()` 原始页面函数、当前 `UI-05.tsx`、UI 注册表、计划投影适配、现有测试。 |
| 允许输出 | 结构化差异清单、受限代码 diff、原图结构契约测试、`check/test/lint` 结果、不可验证项。 |
| 允许写入 | 默认仅 `app/ui/UI-05.tsx`、专属测试、必要的既有图标映射或本地原图裁剪资产；扩展文件必须被任务暂停并请求批准。 |
| 明确禁止 | 修改 Family API、数据库、认证、全局路由、支付/通知/分享、推送、发布、真实会话和生产配置。 |
| 退出条件 | 所有允许的验证通过；原图未覆盖部分写为待确认；生成供人工审阅的 diff，不自动合并。 |

该试点与现有开发节奏一致：原图与原始函数是唯一界面依据，Family API 只复用现有投影，人工继续拥有范围和交付决策。OpenAI 的 Harness 工程经验也强调：代理能力依赖于仓库内可发现的规则、结构化计划、机械验证和反馈循环，而不是无限长提示词。[4]

## 6. 接入前必须作出的决定

1. **运行形态。** 选择先在可控开发环境运行单次 CLI 任务，还是直接建设持续研发工作台。建议先选前者。
2. **授权方式。** 选择交互式 ChatGPT 账号登录或由项目所有者在安全配置界面提供 API 凭据；不得在聊天消息、移动客户端或仓库中保存密钥。Codex 官方支持两类方式。[3]
3. **默认权限。** 批准首个试点采用“工作树读写 + 测试命令白名单 + 无网络副作用 + 无 Git 推送”的最小权限。
4. **审阅门槛。** 明确哪些改动由人工审阅；初期建议所有用户可见 UI、API、数据与政策文件均需人工批准后才进入主分支。

## 7. 建议的下一步

在获得上述四项决策后，创建一个 **Codex Harness 开发试点配置**：短 `AGENTS.md` 只提供仓库地图与强制规则，UI-05 任务规格单独版本化，运行脚本创建隔离工作树并清理临时 token，验证脚本固定输出结构化结果。该设计避免把 Codex 变成“第二个 Family AI 后端”，同时能让其在 legacy UI 原图对齐、测试回归和代码审阅上快速提供可验证产出。
