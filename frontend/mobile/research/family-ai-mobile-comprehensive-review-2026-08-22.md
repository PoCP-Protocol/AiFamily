# Family AI Mobile 全面复盘与优化路线

> **复盘结论。** 当前项目已经是一个具备统一导航、跨页面状态、家庭范围 API 接入和受控开发闭环的 **Family Growth AI Platform 移动端原型**；它不是 35 个彼此孤立的静态页面。但它尚未达到“可将真实家庭、支付、公开社区、专家履约与儿童敏感数据直接投入生产”的程度。下一阶段最重要的不是继续平铺页面，而是完成真实家庭会话、关键链路端到端验证、原图逐页视觉核对和生产化运行保障。

## 1. 复盘范围与证据口径

本复盘只依据当前移动端代码、版本化原图、测试、开发台账和 GitHub 同步结果，不把设计意图、模拟数据或未完成的运行态截图说成真实业务效果。当前代码具有 **35 条 UI 注册记录**，其中 UI-01 位于首页标签页，UI-02 至 UI-35 为 34 个独立页面文件；恢复的 UI 原图目录包含 **52 个版本化文件**，并以清单约束 UI-01 至 UI-35 的编号和来源。[1] [2]

最近一次本机验证结果为：Vitest **76 项通过、1 项既有认证测试跳过**，TypeScript 检查通过，Expo Lint 通过。该结论证明了目前的纯函数、契约、路由、状态和 API 请求层在测试输入下可用；它不等同于真机、真实家庭会话、真实网络和生产外部效果已经验证。[3]

| 维度 | 已核验事实 | 复盘判定 |
|---|---|---|
| 页面边界 | 35 个注册页面均有基线名、功能点、一级标签归属与主要出口；主目标路由文件存在。 | **完整注册，未完成逐页视觉验收**。 |
| 原图资料 | UI-01 至 UI-35 的原图集已恢复；UI-01 至 UI-05 已进入严格逐页对齐循环。 | **资料完整，视觉整改仍在前段**。 |
| 本机状态 | 通过单一 reducer、AsyncStorage 与家庭私有草稿保存行动、测评、服务、商业、社区等状态。 | **可用的 Dev/离线工作层**。 |
| API 接入 | 已接入 Bearer 会话、家庭上下文、成长、商业、服务、平台表面投影与幂等请求。 | **具备真实接入骨架，真实会话回归不足**。 |
| 外部效果 | 支付、通知、公开发布、自动履约和外部分享均保持 no-op 或私有草稿。 | **开发边界明确，生产能力未开启**。 |
| 远程仓库 | 当前移动端内容已同步到 `PoCP-Protocol/family-ai` 的 `main`。 | **代码归档完成**。 |

## 2. 已经实现了什么

### 2.1 产品和导航：一个平台，而不是多套页面

项目将 35 个 UI 组织为“今天、成长、发现、服务、我的”五个移动一级入口；这保留了移动端可用的底部导航，同时把成长、计划、评估、服务、商业、社区六条业务循环落在同一注册表与路由体系中。[1] [4] 首页不再重复实现后续页面业务，而是作为平台总入口，把确认的热区导向后续 UI。

当前已串起的核心路径包括：**UI-01 → UI-02 → UI-03 → UI-04 → UI-05 → UI-09**，以及 UI-35 成长营到今日任务的共享行动路径。UI-13 至 UI-18 使用商业与权益投影；UI-19 至 UI-24 使用服务供给、时段和服务记录投影；UI-25 至 UI-28 以私有小记草稿和已审核经验目录为边界；UI-29 至 UI-34 回读成果、会员、服务、资产和家庭档案。[1] [4]

### 2.2 legacy UI 与原图工作：从“存在页面”走向“逐页对齐”

所有页面均有注册、可解析主要目标和至少四个功能点定义。UI-01 至 UI-05 已进入“先看原图、列差异、再修复”的严格对齐模式：UI-01 重建平台首页热区，UI-02 复原第 2/5 步测评，UI-03 重建成长解读，UI-04 恢复暖橙摘要与四周时间线，UI-05 重建陪跑服务卡、完成度、内容区和打卡出口。UI-05 还加入了不改变路线和内容结构的轻量点击反馈与服务卡加载过渡。[5] [6]

这意味着视觉工作已有正确方法和真实资产，而不是仅根据当前代码反推设计；但 **UI-06 至 UI-35 尚未完成同等强度的逐页原图差异清单、真机同屏核对和修复闭环**。因此不能将“35 页可路由”误称为“35 页像素级对齐”。

### 2.3 数据、状态与 AI-native 基础

移动端的共享状态机已覆盖今日行动、21 天营、测评焦点与回答、孩子选择、成长故事、商品意向、邀请、同行、咨询、活动、私有小记和互动草稿；这些状态通过 AsyncStorage 持久化，支持跨页面回读。[7] 反思被显式标记为 `perspective`，孩子选择为私有视角，行动完成只表示发生，不写成儿童结果、总分或排名。[7] [8]

API 客户端已经统一了 8 秒超时、Bearer 认证、`credentials: omit`、请求快照、空投影识别和错误状态；商业、服务、计划与私有检查草稿命令携带幂等键与关联 ID。[9] 这为未来 Family Digital Twin、Growth OS 和模型网关接入保留了可追溯结构，但当前只在受控投影、规则建议和 no-op/合成状态范围内运行。

### 2.4 真实 API 骨架与 Dev 降级

应用支持账户会话、家庭上下文选择和 SecureStore/localStorage 中的 token 与家庭选择持久化。若未配置 `EXPO_PUBLIC_FAMILY_API_BASE_URL` 或没有有效 token，应用显式进入 `local_synthetic`，而不是悄悄把模拟数据当作线上家庭数据。[10] 这一点是正确的开发体验设计：页面可以演示与测试，但家庭范围、来源和真实会话状态并未被伪造。

### 2.5 测试与用户体验基础

测试覆盖了 legacy UI 注册和主要路由存在性、跨循环状态回读、21 天营三阶段与幂等完成、测评/计划、API Bearer 与幂等请求、商业/服务/社区 no-op 边界、私有内容边界、投影加载/空/失败状态、下拉刷新并发抑制，以及 UI-01 至 UI-05 的原图结构契约。[3] 27 个列表、目录和记录型页面复用原生下拉刷新；加载、刷新、失败、空投影和本机草稿回退已用家长语言表示，而不是暴露工程术语。[11]

## 3. 当前架构判断

### 3.1 当前架构的强项

| 层次 | 当前实现 | 价值 |
|---|---|---|
| 用户界面 | Expo Router + 五标签 + legacy UI 注册表 + Warm Intelligence 视觉。 | 页面不会各自长成孤岛，主出口能统一核验。 |
| 移动领域层 | Context + reducer + AsyncStorage，统一行动、草稿和回读。 | 离线可演示、可恢复，能支撑多页连续旅程。 |
| API 会话层 | Bearer-only、家庭范围上下文、SecureStore、超时、请求快照。 | 为真实家庭会话准备了明确边界。 |
| 投影层 | Core Growth、Platform Surfaces、Commerce、Membership、Service、Plan、Report 等读取适配。 | 避免移动端重建第二套家庭本体。 |
| 受控命令层 | 命名意向/草稿、幂等键、关联 ID、no-op 回执。 | 能在 Dev 中串场景，不误触支付、通知或公开发布。 |
| AI 准备层 | Fact / Perspective / Recommendation / Action 分层；模型状态与来源边界字段。 | 未来可接模型网关，不让自由文本直接写核心状态。 |

### 3.2 当前架构的限制

第一，**状态来源是混合的**。行动、草稿和回读在本机 reducer 中表现良好，但部分后续状态只是合成数据或本机草稿，并非由真实 API 长期保存后再次读取。第二，API 客户端本身可调用很多现有接口，但缺少“真实 token + 真实家庭上下文 + 多次重启 + 断网重试”的系统级验证。第三，项目包含 TanStack Query/tRPC 基础设施，但 Family 领域读取主要通过自定义 Context、手写请求快照和 reducer；这在规模增加后会带来缓存策略、失效策略、并发重试和数据来源可观测性不统一的问题。[9] [10]

> 当前最准确的描述是：**“已完成单一移动端体验层和受控领域适配层；尚未完成生产级数据一致性、端到端运行保障与外部服务履约层。”**

## 4. 还差什么：按严重程度区分

### P0：阻止生产验证的缺口

| 缺口 | 现状 | 为什么重要 | 建议完成标准 |
|---|---|---|---|
| 真实家庭会话 E2E | 代码支持 Bearer 会话，但已知验证以 synthetic/local fallback 和 mock 为主。 | 无法证明真实账号、家庭选择、权限变更与读写回读一致。 | 建立一套可重置的测试家庭；真机完成登录、选家庭、读取、写草稿、重启回读、401、断网恢复。 |
| Native 真机回归 | 管理预览多次没有提供可截图 URL；尚未形成 iOS/Android 真机证据。 | 动画、Safe Area、键盘、下拉、触感、滚动与字体缩放可能和 Web 不同。 | iOS 与 Android 各跑一次关键行动矩阵，保存截图/录屏与缺陷单。 |
| UI-06 至 UI-35 逐页视觉核对 | 完整原图已经恢复，但只完成 UI-01 至 UI-05 的严格对齐。 | 产品目标要求严格按照原图，不能仅以注册表完成度代替。 | 每页形成“原图证据 → 差异 → 修复 → 截图/替代证据 → 契约”的记录。 |
| 远程 CI/CD 结论 | GitHub 代码已同步，但当前 GitHub token 对 Actions/Check Runs 返回 403，公开浏览器页也不可访问私有 Actions。 | 不能据此宣称远程构建和测试已全部通过。 | 由具备 Actions read 权限的账号检查最新 run，或补齐仓库工作流、required checks 和可读 token。 |

### P1：影响规模化维护与真实数据质量的缺口

| 缺口 | 风险 | 优化方向 |
|---|---|---|
| API 合同与投影版本治理 | `DEV_*` 投影与手写泛型在后端演进时可能静默失配。 | 从共享 contracts 生成 DTO/校验器；每个投影声明版本、兼容性和弃用策略。 |
| 本机草稿的同步策略 | 同一家庭跨设备时可能重复、覆盖或无法解释来源。 | 增加草稿 ID、修订号、同步状态、冲突策略和明确“仅此设备”提示。 |
| 服务/商业命令的状态机 | 现在的意向和 no-op 合理，但从意向到真实预约/支付尚无正式迁移图。 | 分别定义 Intent → Reviewed → Confirmed → Fulfilled/Cancelled，所有外部效果经 adapter 与 audit。 |
| 观测性 | 请求快照已有，但缺少统一性能、错误分组、命令审计检索和敏感字段脱敏策略。 | 引入结构化客户端事件、错误边界、trace/correlation ID 对齐和隐私脱敏日志。 |
| 自动化 UI 验证 | 当前以源代码契约为主，不能发现真实布局/溢出/字体问题。 | 构建稳定的本地/真机截图基线，按页面与关键状态做视觉差异。 |

### P2：体验与工程质量优化项

| 机会 | 当前状态 | 优化建议 |
|---|---|---|
| 列表性能 | 有 27 页下拉刷新，部分页面仍以 `ScrollView` 和静态内容组织。 | 对长社区、活动、资产、服务记录切换 `FlatList`，加入分页和空白骨架。 |
| 可访问性 | 关键按钮已有标签，但没有全页屏幕阅读器与 Dynamic Type 系统证据。 | 建立 Accessibility label、focus order、字体放大、颜色对比和触达尺寸测试清单。 |
| 动画一致性 | UI-05 已有可验证的轻量反馈，其他高频主动作尚未统一。 | 设定 80–300ms、0.95–0.98 缩放、必要时触感的通用交互规则。 |
| 依赖卫生 | Expo 日志提示若干包与 SDK 推荐版本不一致；Lint 有 `eslint.config.js` 模块类型警告。 | 单独建立依赖升级分支，按 Expo compatibility 检查更新；明确 ESM/CJS 配置，消除 lint 性能警告。 |
| 内容配置化 | 21 天营、90 天计划、服务/商业样例已有模块，但局部仍含界面示例文案。 | 把可运营内容放入版本化内容目录和后端投影，页面只负责展示。 |

## 5. 不应被误判为“已完成”的事项

下列事项在 Dev 目的下被刻意限制；它们不是简单补一个按钮就能完成的功能：

1. **支付、退款、自动续费。** 当前仅保存意向或内部开发回执，没有扣款、开票或外部支付。
2. **专家预约与履约。** 当前可保存咨询需求和服务意向，但不占用真实时段、不通知专家、不产生真实服务承诺。
3. **公开社区与互动。** 当前小记、收藏、关注、回应均处于私有/受控草稿范围；不存在真实公开发布、评论计数或外发通知。
4. **儿童诊断、家庭排名与总分。** 这三项被设计和测试明确排除，不能为“看起来更智能”而重新加入。
5. **AI 自动改写核心事实。** 模型/规则仅能形成解释、标签或草稿建议；事实、会员、订单、服务与结果仍必须经过命名行动、政策与来源确认。

## 6. 建议的优化路线

### 第一轮：把“可演示”提升为“可验证”（优先执行）

1. **完成 UI-06 至 UI-12 原图对齐。** 先跑成长主线：会员/服务状态、测评入口、报告、任务、孩子小助手、成长节奏与故事卡；每页只依据原图和原始热区，完成后立即保存检查点。
2. **建立真实家庭会话回归。** 用受控测试家庭执行 UI-01 → UI-09、UI-02 → UI-05、UI-13 → UI-18、UI-19 → UI-24、UI-25 → UI-28 四条链路，覆盖登录、家庭切换、重启、401、超时和本机回退。
3. **解决 CI 可观测性。** 获得 GitHub Actions `read` 权限，确认是否已有工作流；若没有，则在目标仓库增加移动端 `check/test/lint` 工作流，并设为 main 的 required check。
4. **补真机证据。** Android/iOS 各验证至少 10 个关键页面状态，包括 UI-05 打卡动效、Safe Area、下拉刷新、键盘输入和断网提示。

### 第二轮：把“受控草稿”提升为“可协作数据”

1. 为测评、行动、咨询、活动、商业意向和社区私有小记定义统一 `DraftEnvelope`：ID、版本、来源、可见性、同步状态、冲突策略、审计引用。
2. 将 Family API 的投影类型沉淀到共享 contracts，移动端改用显式 schema 校验和兼容版本处理。
3. 为所有命名行动增加“本机已保存 / 同步中 / 已接收 / 需重试 / 被拒绝”的用户语言反馈，而不是仅靠内部状态。
4. 把 UI-29、UI-33、UI-34 连接到可审计的过程事件，不把过程记录自动升级成结果结论。

### 第三轮：在明确业务批准后，逐项打开外部能力

1. **服务。** 先实现专家可用时段锁定与人工确认，再实现真实通知和履约回读。
2. **商业。** 先实现权益、订单和退款状态的只读回读，再通过支付 adapter 逐步启用支付；移动端不直接承载支付机密。
3. **社区。** 先完成内容审核、可见性、举报和审计，再考虑公开发布与通知。
4. **AI。** 先建设模型网关评估、提示版本、证据来源和人工复核，再扩大建议能力；不得让模型直写儿童或家庭核心结论。

## 7. 最终判断

项目最有价值的成果不是单页数量，而是已建立的共用骨架：**单平台导航、单一移动状态机、家庭范围 API、受控草稿/命名行动、证据边界和六大业务循环的共同语言。** 接下来应停止用“再做几个页面”衡量进度，改用“一个真实家庭能否在真机上跨页面完成、恢复、解释和回读一次完整旅程”衡量质量。

从产品与工程投入比看，推荐的下一项具体工作是：**先完成 UI-06 至 UI-12 的严格原图对齐，同时建立真实家庭会话的关键链路回归矩阵。** 这会把首页、测评、成长计划、陪跑、任务、孩子参与、节奏和故事真正连成家庭成长主线，再进入商业、服务和社区的生产化。
