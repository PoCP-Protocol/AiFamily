# ADR-0006: 未成年人数据合规约束进入架构（不是法务附录）

- **Status**: Accepted
- **Date**: 2026-08-29
- **Deciders**: project-owner / chief-architect
- **Supersedes**: null
- **Superseded By**: null

## Context

AiFamily 的核心数据主体是**家庭与未成年人**，这使它落入中国法规密度最高的数据场景之一。

以下条款经 deep-research 对抗性核验（每条声明 3 票独立验证，2/3 推翻即淘汰）**逐字确认**，记录于 `docs/12_governance/COMPLIANCE_HARD_CONSTRAINTS.md`。核验同时纠正了若干常见误解（见下），这些纠正本身就是不能靠常识推导的证据。

核验的关键处罚事实：PIPL 第 66 条的处罚梯度中，**"责令暂停或终止提供服务"在第一档即可适用**——不以"拒不改正"或"情节严重"为前提。也就是说合规失败的后果不是罚款，是业务被叫停。

**为什么这必须是架构决定而不是法务清单**：上述约束中至少四条直接决定数据模型与领域边界——删除的级联范围、自动化决策的人工复核路径、商业主体是谁、LLM 供应商的部署形态。这些无法在功能建成后"补上合规"，因为它们改的是 schema 与域边界。

## Decision

以下六条作为**架构级硬约束**进入 AiFamily，与宪章条款同级，不可由产品需求推翻。

### 1. 14 岁以下全部个人信息 = 敏感个人信息，须过必要性检验
**法源**：PIPL 第 28 条——敏感个人信息"包括…以及不满十四周岁未成年人的个人信息。只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下…方可处理。"

**架构含义**：必要性检验（第 28 条）与监护人同意义务（第 31 条）**两者累加，不可互替**。**拿到监护人同意 ≠ 通过必要性检验。** 每一个采集 14 岁以下数据的字段都必须能回答"为什么这个字段是必要的"，而不是"家长同意了"。

**核验纠正**：14 岁分界线来自 **PIPL 第 28/31 条，不是**《未成年人网络保护条例》——条例全文"十四周岁"**零命中**。引错法源会导致约束范围判断错误。

### 2. AI 评估输出构成自动化决策 → 可解释 + 可拒绝 + 人工复核 + DPIA 留存 ≥3 年
**法源**：PIPL 第 73 条第 2 项定义自动化决策为"通过计算机程序自动分析、评估个人的行为习惯、兴趣爱好或者经济、健康、信用状况等，并进行决策的活动"——涵盖基于儿童行为/健康信号的评估。第 24 条第 3 款逐字："个人有权要求…予以说明，并有权拒绝…**仅**通过自动化决策的方式作出决定"。第 55 条：**"处理敏感个人信息"与"利用个人信息自动化决策"两项分别独立触发** DPIA；第 56 条要求报告与记录**至少留存三年**。**AiFamily 两项同时成立。**

**架构含义**：这条与 ADR-0005（AI 原生）直接咬合，且与宪章 R9 同向——**R9 的四层区分（Fact/Perspective/Recommendation/Action）不只是产品设计选择，它同时是"非仅自动化决策"的法律实现路径**。AI 输出停在 Perspective 层、须家庭 Named Action 确认才成为事实，这个设计恰好满足"可拒绝仅自动化决策"。DPIA 需要**真实的评估文档与记录机制，不是一次性文档**。

### 3. 绝对禁止：向未成年人自动化决策商业营销
**法源**：《未成年人网络保护条例》第 24 条第 3 款——"不得**通过自动化决策方式向未成年人进行商业营销**"。核验确认这是**绝对禁止型条款，无例外、无年龄细分**（适用全部未成年人，不限 14 岁以下）。

**架构含义**：**孩子端商业化路径被实质关闭。** 积分商城、会员权益推送、个性化推荐商品等一律不得面向孩子端。**商业主体必须是家长。**

**核验纠正的误解**：家长端并非完全豁免——仍受 PIPL 第 24 条第 2 款约束，须提供非个性化选项或便捷拒绝方式，且第 55 条 DPIA 义务同样适用。

### 4. 向量 / embedding 等派生数据的删除是法定义务
**法源**：《儿童个人信息网络保护规定》第 19 条（更正权）、第 20 条（删除权，四项触发："包括但不限于"监护人撤回同意 / 终止使用服务 / 超出目的范围或必要期限 / 违法违约处理）、第 23 条（停止运营须立即停止收集并删除全部儿童个人信息）。第 28 条仅豁免"无法识别为儿童个人信息"的自动留存数据。

**核验的关键推论**：按孩子维度派生的**画像向量 / embedding 仍属可识别儿童个人信息**，落入第 20 条删除对象。

**架构含义**：原始数据删除 → 对应 embedding 必须同步删除。这是**级联删除的设计要求，必须在向量层建立前就写入数据架构**（`docs/07_data/`），否则事后无法建立原始记录与向量的对应关系。这也直接影响 ADR-0005 判据 2/4（学习闭环、语义化数据结构）的实现方式：沉淀的证据必须可定向删除，不能是不可解构的聚合权重。

### 5. 委托第三方处理不得转委托（对 LLM 供应商选型的硬约束）
**法源**：《儿童个人信息网络保护规定》第 16 条——委托第三方处理须**先做安全评估**、签委托协议、受托方**不得超出授权范围**、**不得转委托**、委托关系解除时及时删除；第 17 条：向第三方转移另须做安全评估。

**架构含义**：调用外部 LLM / 向量服务属"委托第三方处理"。**"不得转委托"对架构有实质约束：多数 LLM 厂商在第三方云上再分包。** 因此可能需要：涉未成年人数据的推理请求先脱敏，或选择可承诺不转委托的部署形态（私有化 / 专属实例）。**这条可能限制可用供应商范围，需法务与商务介入评估分包结构。**

### 6. 同意的单独性与目的绑定
**法源**：PIPL 第 29 条（单独同意）与第 14 条第 2 款（目的/方式/种类变更须重新取得同意）。

**架构含义**：不得把多个处理目的打包进一次同意。同意撤回必须即时生效（`backend/platform/consent` 的 `ConsentGate` 是这条的载体）。

### 附：核验确认的一条边界
PIPL 全文"监护人"仅出现 1 次（第 31 条）；第 44/45 条的知情权/查阅复制权授予"个人"而**无监护人代行条款**——故 **PIPL 本身不赋予家长查看 14 岁以上孩子数据的权利**。这与产品直觉相反，是隐私线设计的依据。

## Alternatives Considered

### A. 合规作为发布前的检查清单，不进入架构
**支持理由**：这是行业常规做法。合规要求变化快，写进架构会让架构跟着法规版本变；且大部分合规义务（隐私政策、同意弹窗、数据主体请求流程）确实是产品层与流程层的事。

**否决理由**：上述六条中**至少四条无法在事后补**：
- 第 4 条（embedding 级联删除）改的是 schema 与向量层设计。向量建成后再补对应关系，等于要为每个已存在的向量反查它派生自哪条原始记录——若当初没存这个关联，物理上做不到。
- 第 3 条（禁止向未成年人自动化营销）改的是**商业主体归属**，决定 commerce 域的 Owns 边界。事后改等于重做商业模式。
- 第 2 条（可拒绝仅自动化决策）改的是 AI 输出的数据模型层级。
- 第 5 条（不得转委托）改的是供应商选型与部署形态，可能要求私有化部署——这是基础设施决定。

"事后补合规"只对流程性义务有效，对结构性义务无效。

### B. 只做最低合规（拿到监护人同意即可）
**支持理由**：实现成本最低，且监护人同意是最直观、用户最能理解的合规形态。

**否决理由**：核验明确纠正了这个误解——**必要性检验（第 28 条）与监护人同意（第 31 条）两者累加，不可互替**。拿到同意不豁免必要性检验。且第 24 条第 3 款的"可拒绝自动化决策"与第 3 条的绝对禁止条款**都不因同意而豁免**：绝对禁止型条款无例外，家长同意向孩子做自动化营销也不合法。

### C. 论证 AiFamily 不适用《未成年人网络保护条例》第 28 条（在线教育适龄）
**支持理由**：若 AiFamily 名义服务对象是**家长**而非未成年人，可能落在第 28 条（要求以未成年人为服务对象的在线教育按年龄阶段特点提供产品）之外。这个论证有一定基础。

**否决理由**：**设计上不宜过度依赖这一点。** 第 44 条列举含"等"字，监管可类推适用。合规文档明确记录了这个判断：商业化（COMMERCE 闭环）**应主动实现消费限额能力，而不是论证自己不适用**。把合规建立在"我们不属于这个类别"的论证上，是把业务连续性押在监管解释上。

### D. 数据完全本地化 / 不使用外部 LLM
**支持理由**：一次性解决第 5 条（不得转委托）与第 4 条（删除权）的大部分难题，数据不出域。

**否决理由**：与 ADR-0005（AI 原生）直接冲突——核心域的智能依赖前沿模型能力，自建模型在当前阶段无法达到可用水平。**保留为部分方案**：涉未成年人数据的推理请求可走脱敏后再出域，或对最敏感路径采用私有化/专属实例部署。这是折中而非替代，且这个张力（AI 能力上限 vs 供应商约束）**尚未解决**。

## Consequences

### 正面
- 合规约束成为可引用的架构条款，产品设计冲突时有明确的一票否决依据。
- 与既有治理同向而非额外负担：R9（AI 输出不得成为事实）恰好是第 2 条的实现路径；R6（无审计不改状态）恰好是 DPIA 留存的载体；`backend/platform/consent` 的 `ConsentGate` 恰好是第 6 条的载体。**合规与既有伤疤驱动的护栏在此重合，是本决定成本最低的部分。**
- 提前关闭了一条会走很远才发现不合法的商业路径（孩子端商业化）。

### 负面 / 代价
- **孩子端商业化路径被实质关闭，商业主体必须是家长。** 这是真实的商业模式约束，不是技术约束。既有商业设想中"积分商城/会员权益向孩子端推送"一类必须改为仅家长端 + 非个性化选项。
- DPIA 需要机制化（评估流程 + 记录留存 ≥3 年），不是一次性文档——这是持续运营成本。
- embedding 级联删除给向量层增加设计复杂度：必须维护原始记录 ↔ 派生向量的可追溯映射，且删除必须原子。
- 第 5 条（不得转委托）**需法务与商务介入**评估 LLM 供应商分包结构，可能限制供应商范围或要求私有化部署，进而影响 AI 能力上限与成本结构。

### 需要接受的风险
- **法规解释存在不确定性**。第 44 条的"等"字、第 28 条对"以未成年人为服务对象"的界定，都留有监管类推空间。本决定采保守解读（例如"AI 成长报告展示给家长"判为"允许但须配套可解释+可拒绝+人工复核+DPIA"），但保守解读也可能被认为不足。
- **"不得转委托"在现实中难以完全核实**：LLM 厂商的实际分包结构对客户不透明。即使签了协议，也难以验证受托方是否再分包。这是无法通过架构消除的风险。
- 与 ADR-0005 的张力未解决：AI 原生要求最强模型能力，合规要求最可控部署形态，两者当前无同时最优解。
- **PIPL 不赋予家长查看 14 岁以上孩子数据的权利**这一发现，与"家庭平台家长可见"的产品直觉直接冲突，可能在产品设计中被无意违反。

## Enforcement

**当前仅为意图，零机械执行。这是本仓库最严重的执行缺口之一——因为这六条的违反后果是业务被叫停，而不是测试变红。**

现状：
- `docs/12_governance/COMPLIANCE_HARD_CONSTRAINTS.md` 是一份人类可读文档。**没有任何架构测试引用它。**
- 部分间接载体已存在但未与合规条款绑定：`backend/platform/consent`（`ConsentGate`，对应第 6 条）、`backend/platform/audit`（`AuditRecorder`，是 DPIA 记录的潜在载体）、`backend/platform/authorization`（`PolicyEngine`，fail-closed）。这三者有代码有测试，但**测试断言的是通用行为，不是合规约束**。
- 宪章 R8（高影响行为必须过闸，含"涉未成年人的敏感动作"）在第 2 节标注为"Wave 1–5 逐步接入"，当前无测试。
- 数据层（`docs/07_data/`）尚未建立，embedding 级联删除无处可执行。

**按 R14 的标准，这六条目前"只是意图，不是护栏"。** 补齐路径（优先级应高于多数功能开发）：
1. **第 3 条（绝对禁止）最容易也最该先机械化**：加架构测试断言 commerce 域的任何推荐/营销路径不接受未成年人 subject。这是一条否定断言，实现成本低。
2. 给 `DOMAIN_REGISTRY.yaml` 增加 `minor_data: true/false` 字段，并加测试断言涉未成年人数据的域必须声明其 consent scope 与删除级联路径。
3. `docs/07_data/` 建立时，把"每个存储未成年人派生数据的表必须登记其级联删除路径"写成 registry + 架构测试。
4. DPIA 记录用 `backend/platform/audit` 承载，加测试断言自动化决策事件必带 DPIA 关联字段。
